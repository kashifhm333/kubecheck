# KubeCheck — Offline Update and Signing

**Document ID:** UPDATE-SIGN-001 · **Status:** Normative — Approved · **Version:** 1.0.0 · **Owner:** Software Supply-Chain Security · **Last reviewed:** 2026-10-31

This document specifies the offline-compatible knowledge update and signing mechanism for KubeCheck. It defines how a knowledge bundle is signed, how the signature is verified, how the signing keys are distributed and rotated, how the bundle is ordered and anti-rollback-protected, how it is activated atomically with preservation of the last-known-good bundle, how it is transported across an air gap on removable media, how a compromised bundle is revoked, and how every one of these operations is audited. It also specifies the distinction the rest of the document depends on: a **checksum** detects corruption relative to a trusted digest, and a **digital signature** authenticates signed metadata under a trusted key. The two are often conflated in developer tooling and the conflation is a security bug, because a checksum without a trusted digest proves nothing and a signature without a trusted key proves nothing; the document is careful to use each term only for its proper purpose.

Every requirement in this document is identified with the prefix `UPDATE-SIGN-REQ-NNN`, every key-management operation with `KEY-OP-NNN`, every failure mode with `UPDATE-FAIL-NNN`, every test with `UPDATE-SIGN-TEST-NNN`, and every cryptographic test vector with `TEST-VECTOR-NNN`. The document uses non-production example keys throughout, and it states explicitly and repeatedly that **no private signing key is ever committed to a repository, embedded in a package, shipped in a client binary, or stored in a location that a build pipeline can read**. That prohibition is the first requirement in the document and it is restated in every section where a key is mentioned, because the failure mode (a leaked private key) is catastrophic and silent: a leaked key lets an attacker forge any bundle and the user has no way to detect the forgery until the key is revoked.

## The trust model, stated precisely

KubeCheck's update mechanism rests on three trust anchors that are established out-of-band and that the tool never modifies during an update.

The first trust anchor is the **root of trust**, which is a public key distributed with the engine at install time. The root of trust is the key against which every release signature is ultimately verified. It is distributed through the engine's installation channel (the pip package, the Krew plugin archive, the standalone binary) and it is verified by the same signature mechanism that verifies the engine binary itself. The root of trust is a public key; the corresponding private key is held in an offline hardware security module (HSM) or an air-gapped signing host, and it is used only to sign release keys, not to sign bundles directly. This two-level hierarchy (root key signs release keys; release keys sign bundles) is specified because a single-level hierarchy would require the root key to be online for every bundle release, which increases the root key's exposure surface unnecessarily.

The second trust anchor is the **release key set**, which is a set of one or more public keys, each signed by the root key, that are used to sign bundles. The release key set is distributed as part of the engine and as part of each bundle's signature metadata. A bundle signed by a release key whose public key is in the release key set (and whose signature by the root key verifies) is a valid bundle. A bundle signed by a key that is not in the release key set is rejected regardless of whether the bundle's own metadata claims the key is valid.

The third trust anchor is the **user's trust anchor file**, which is the file on the user's machine that contains the root key's public key and the current release key set. The user's trust anchor file is created at install time and is updated only by the release mechanism described in the key-rotation section; it is not updated by the update mechanism. This separation is deliberate: an attacker who can serve a malicious bundle cannot also serve a malicious trust anchor, because the trust anchor is not fetched by the update mechanism.

`UPDATE-SIGN-REQ-001` requires that the trust anchors be established out-of-band from the update mechanism. `UPDATE-SIGN-REQ-002` requires that the trust anchor file be signed by the root key and that the engine verify the signature before using the trust anchor. `UPDATE-SIGN-REQ-003` requires that a bundle whose signature does not verify against the release key set cause the bundle to be rejected with a `fatal` error naming the signer and the reason, and that the prior bundle (if any) remain active.

## Checksums versus digital signatures: the distinction the document depends on

A checksum is a hash of some content. Its purpose is to detect **corruption**, meaning an unintentional change that occurred during storage or transport. A checksum is only meaningful when it is compared against a **trusted digest** — a digest that the verifier already knows to be correct, obtained through a channel independent of the content being checked. A checksum without a trusted digest is a self-reference: the sender computes the hash and sends both the content and the hash, and the receiver recomputes the hash and compares; this detects corruption but it does not detect malicious substitution, because an attacker who can modify the content can also modify the hash. The tool that ships a checksum over HTTPS to the same server that serves the content is protecting against network corruption, not against a compromised server.

A digital signature is a cryptographic operation that uses a **private key** to produce a value over some content, and that a **public key** can verify. Its purpose is to **authenticate** the content as having been produced by the holder of the private key, and to detect **any** modification to the content, whether caused by corruption or by an attacker. A signature is only meaningful when it is verified against a **trusted public key** — a key that the verifier already trusts, obtained through a channel independent of the signed content. A signature without a trusted public key is worthless: it proves that some key signed the content, but not that the key belongs to anyone the verifier should trust.

`UPDATE-SIGN-REQ-004` requires that the tool use checksums for corruption detection and signatures for authentication, and that the tool never rely on a checksum alone to authenticate a bundle. `UPDATE-SIGN-REQ-005` requires that the tool's user-facing documentation state the distinction explicitly, so that a user who reads "verified" understands whether the verification was a checksum comparison (corruption detection) or a signature verification (authentication). The help text of `kubecheck bundle verify` must state that the command performs both checks, and that a checksum-only verification is not sufficient for security.

The practical consequence is that the checksum in a bundle's manifest (`KNOWLEDGE-REQ-041`) is used to detect corruption of individual files during transport, but the bundle's security comes from the signature (`KNOWLEDGE-REQ-042`, `KNOWLEDGE-REQ-043`). A bundle whose files all match their declared checksums but whose signature is invalid is a bundle that has been tampered with in a way that preserved the file contents; the checksum passes and the signature fails, and the signature failure is the one that matters.

## Trusted signing-key distribution and key rotation

The signing-key distribution mechanism has three components: the initial distribution of the root key, the distribution of the release key set, and the rotation of both.

The root key's public key is distributed with the engine at install time. `UPDATE-SIGN-REQ-006` requires that the root key's public key be embedded in the engine binary as a compile-time constant, and that the engine verify the root key's fingerprint against a second, independently published value (the fingerprint is published on the project's website and in the project's release notes; the engine's `--version` output displays it, and the user can compare the displayed fingerprint against the published one to detect a compromised engine). The embedding is not a security mechanism by itself — an attacker who can replace the engine binary can also replace the embedded key — but it establishes the starting point of the trust chain, and the fingerprint comparison gives the user a way to verify that the engine they installed is the engine the project published.

The release key set's public keys are distributed as part of the engine and as part of each bundle. `UPDATE-SIGN-REQ-007` requires that the release key set be a file (`trust/release-keys.json`) embedded in the engine and mirrored in each bundle's signature metadata, and that the file contain, for each release key, the public key, the key ID, the validity period, and the root key's signature over the release key. The engine verifies the root key's signature over each release key before adding the release key to the trusted set, and the engine refuses to use a release key whose root signature does not verify.

`UPDATE-SIGN-REQ-008` requires that the release key set be rotation-tolerant: the set may contain more than one active release key at any time, and a bundle is accepted if it is signed by any active release key. The rotation procedure adds a new release key to the set before the old key is retired, so that bundles signed by either key are accepted during the rotation window.

Key rotation proceeds in four phases. In the **announcement** phase, the project publishes the new release key's public key, its key ID, its intended validity period, and the date on which it will become active. In the **activation** phase, the new release key is added to the release key set in a new engine release, and bundles signed by the new key begin to be published; the old key remains in the set. In the **retirement** phase, the old key is removed from the release key set in a subsequent engine release, after the validity period of every bundle signed by the old key has ended. In the **revocation** phase, if the old key is compromised before its scheduled retirement, the old key is removed immediately and every bundle signed by it is rejected; the revocation section specifies the emergency procedure.

`KEY-OP-001` requires that a new release key be signed by the root key before being added to the set. `KEY-OP-002` requires that the root key's signature over the release key cover the release key's public key, key ID, and validity period, so that an attacker cannot substitute a different validity period. `KEY-OP-003` requires that key rotation be announced at least one engine minor release before the new key becomes active, so that users have time to update their engines. `KEY-OP-004` requires that a release key's validity period not exceed two years, so that a compromised key's blast radius is bounded. `KEY-OP-005` requires that the root key be rotated at least every five years, using the same announcement and activation phases, and that the new root key be cross-signed by the old root key so that engines that trust the old root key can transition to trusting the new root key without a full reinstall.

The private keys corresponding to the root key and the release keys are never present in the repository, the package, the binary, or the build pipeline. `UPDATE-SIGN-REQ-009` states this prohibition explicitly: no private signing key is ever committed, embedded, shipped, or stored in a location that the build pipeline can read. The root key is held in an HSM or an air-gapped signing host that is not connected to the network; the release keys are held in a signing service that requires multi-party approval for each signing operation, or in a hardware token that the release manager inserts for the signing ceremony. The signing ceremony is documented in `docs/distribution/SIGNING_CEREMONY.md` (a separate document) and produces an audit log entry for every signature.

## Digital signatures and authenticated metadata

The bundle signature scheme is specified in `KNOWLEDGE_BUNDLE_FORMAT.md` and restated here in the update context. The bundle manifest (`manifest.json`) declares the bundle's contents, the bundle's version, the engine compatibility range, the Kubernetes version coverage, the file list with per-file hashes, the provenance, and the signature metadata. The signature covers the canonical serialization of the manifest with the signature field omitted, concatenated with the sorted list of `(path, sha256)` pairs. The algorithm is Ed25519 in the MVP. The signature is stored in `signature.ed25519` at the bundle root and is mirrored in the manifest's `signature.value` field for redundancy (a bundle whose manifest signature field and signature file disagree is rejected).

`UPDATE-SIGN-REQ-010` requires that the signature cover every file's hash, so that an attacker who modifies a file cannot preserve a valid signature by also modifying the manifest. `UPDATE-SIGN-REQ-011` requires that the signature cover the bundle's `bundle_version`, so that an attacker cannot downgrade a bundle by serving an older bundle with the same content but a lower version (this is one of the two rollback defenses; the other is the version-ordering rule below). `UPDATE-SIGN-REQ-012` requires that the signature cover the bundle's `engine_compatibility` range and `kubernetes_versions` list, so that an attacker cannot substitute a range that matches a vulnerable engine or a version list that omits a security-critical schema.

The authenticated metadata is the set of fields the signature covers. The authenticated metadata includes: the format version, the bundle version, the bundle ID, the engine compatibility range, the Kubernetes version coverage, the generation metadata (timestamp, generator version, source commit, reproducible flag), the provenance list, the file list with hashes, the partitions, the limits, the licenses, and the release key ID. The authenticated metadata does **not** include the signature itself (that would be circular) and does not include any field that the engine derives at load time. `UPDATE-SIGN-REQ-013` requires that the engine's verifier construct the canonical serialization from the authenticated fields exactly as the signer did, and that any discrepancy between the signer's and verifier's serialization be a rejection.

## Hash verification and archive integrity

The bundle is transported as a `.tar.gz` or `.zip` archive. The archive's integrity is protected by two mechanisms: the archive's own checksum and the bundle's internal file hashes.

The archive's checksum (`<archive>.sha256`) is published alongside the archive and is recorded on the transfer document. On the isolated machine, the user verifies the archive's checksum before extraction. This detects transport corruption. The checksum is **not** a signature; it does not authenticate the archive as having come from the project. The archive is authenticated by the bundle's internal signature, which is verified after extraction.

`UPDATE-SIGN-REQ-014` requires that the archive be verified before extraction, and that the extraction itself use the same archive-safety rules as the input resolver (`SEC-YAML-REQ-027`): no path traversal, no absolute paths, no symlinks, no device files, no FIFOs. A malicious archive is a threat regardless of its checksum, and the extraction must be safe against a malicious archive even if the checksum verifies (an attacker who can substitute the archive can also substitute the checksum).

`UPDATE-SIGN-REQ-015` requires that the bundle's internal file hashes be verified after extraction and before activation, and that any mismatch be a rejection with a `fatal` error naming the file and the expected and actual hashes. This is the mechanism that detects a tampered file within an archive whose outer checksum was replaced by an attacker: the outer checksum passes (because the attacker computed it over the tampered archive), but the internal hash fails because the attacker cannot produce a matching signature.

The distinction between the archive checksum and the bundle's internal signature is the distinction between the two mechanisms described above: the checksum detects corruption, the signature detects tampering. A user who sees "archive checksum verified" should understand that this is a corruption check, not a security check, and should continue to verify the signature after extraction. `UPDATE-SIGN-REQ-016` requires that the `bundle verify` command perform both checks and report both results separately, so that the user sees the distinction in the tool's own output.

## Compatibility checks before installation

Before a bundle is activated, the engine performs a sequence of compatibility checks that determine whether the bundle can be used at all. These checks are specified in `KNOWLEDGE_BUNDLE_FORMAT.md` and restated here because they interact with the update mechanism.

The first check is the **format version check**: the bundle's `format_version` must be in the engine's supported set. A bundle with a newer format version than the engine supports is rejected with an error naming the format version and the engine's supported range; the user's recovery action is to upgrade the engine or to obtain a bundle with a compatible format version.

The second check is the **engine compatibility range check**: the bundle's `engine_compatibility.min_version` and `.max_version` must include the engine's own version. A bundle outside the range is rejected with an error naming the range and the engine's version; the user's recovery action is to upgrade or downgrade the engine to a version within the range.

The third check is the **Kubernetes version coverage check**: the bundle must list at least one `supported` Kubernetes version, and the user's requested target version (if supplied) must be in the bundle's list. A bundle that does not cover the target version is not necessarily rejected — a bundle that covers the target version as `deprecated` is accepted with a warning — but a bundle that does not list the target version at all is rejected, and the user is told which versions the bundle covers.

`UPDATE-SIGN-REQ-017` requires that the compatibility checks be performed before the bundle is activated, so that an incompatible bundle never becomes the active bundle and never displaces a working bundle. `UPDATE-SIGN-REQ-018` requires that a compatibility failure preserve the prior bundle and report the failure with a specific error naming the failed check and the values involved.

## Version ordering and anti-rollback controls

The anti-rollback mechanism prevents an attacker from serving an older, still-signed bundle that contains a known vulnerability. The mechanism has two components: a monotonically increasing `bundle_version` in the bundle manifest, and a recorded `bundle_version` of the active bundle in the local bundle store.

`UPDATE-SIGN-REQ-019` requires that the bundle's `bundle_version` be a positive integer that is greater than the previous bundle's `bundle_version` for the same signer. The signer's counter is maintained by the project's release process and is recorded in the release notes; the bundle's manifest declares it, and the signature covers it, so an attacker cannot lower it without invalidating the signature.

`UPDATE-SIGN-REQ-020` requires that the loader compare the incoming bundle's `bundle_version` against the active bundle's `bundle_version`, and reject the incoming bundle if it is lower. The rejection message names both versions and states that a rollback attempt was detected. The loader does not offer an override flag for this check, because an override flag would let an attacker who has compromised the user's configuration (or a user who has been socially engineered) bypass the protection. If a legitimate rollback is needed — for example, because a new bundle introduced a regression — the rollback is performed through the explicit `bundle rollback` command (specified below), which is a separate operation with its own audit trail.

`UPDATE-SIGN-REQ-021` requires that the loader handle the case where the incoming bundle's `bundle_version` equals the active bundle's. This case occurs when the user re-activates the same bundle (idempotent activation, `NET-REQ-011`); the loader verifies that the bundle's signature and content match the active bundle's, and if they do, treats the activation as a no-op; if they do not, the loader rejects the activation with an error stating that two bundles with the same version have different content, which is a defect in the project's release process and must be investigated.

`UPDATE-SIGN-REQ-022` requires that the active bundle's `bundle_version` be recorded in the bundle store's metadata (`bundle-store/metadata.json`) and that the metadata be read at load time to perform the comparison. The metadata is protected by the store's restrictive permissions (`SAFE-EXEC-REQ-047`) and by an integrity check (the metadata file's hash is stored in a separate `metadata.sha256` file, and the loader recomputes the hash; a mismatch is a corruption error, not a tampering error, and the loader falls back to the bundle store's transaction log to reconstruct the metadata).

The anti-rollback protection is not the same as a freshness check. A bundle can be fresh (recently generated) and still have a lower `bundle_version` than the active bundle if the active bundle was generated by a different signer with a higher counter. The anti-rollback check compares versions within the same signer; a bundle from a different signer is a different trust domain, and the loader's trust anchor set determines whether the different signer is trusted. `UPDATE-SIGN-REQ-023` requires that the loader handle multiple signers by maintaining a separate `bundle_version` counter per signer, so that a signer transition does not accidentally trigger a rollback rejection.

## Freshness policies and intentionally permitted offline exceptions

The freshness policy determines when a bundle is considered stale and what the tool does about it. The policy is designed for the offline-first use case, where an air-gapped user may legitimately use a bundle that is months old because the air gap makes frequent updates impractical.

`UPDATE-SIGN-REQ-024` requires that every bundle declare a `fresh_until` date in its `generation` object, which is the date after which the bundle's schemas and rules are considered stale. The date is set at bundle generation time and is covered by the signature. The default is 180 days from the generation timestamp, but the project may extend it for bundles that are known to remain valid (for example, a bundle covering a Kubernetes version that has reached end-of-life and will not receive new schemas).

`UPDATE-SIGN-REQ-025` requires that the loader emit a `warning`-severity finding when the active bundle is past its `fresh_until` date, stating the date, the current date, and the fact that the bundle may be missing recent security findings. The warning does not block analysis; the user can continue with the stale bundle knowingly. This is the "intentionally permitted offline exception": an air-gapped user cannot be expected to update a bundle that requires network access, and blocking analysis would be a worse outcome than running stale knowledge.

`UPDATE-SIGN-REQ-026` requires that the warning be repeated in the report header and in the `version` output, so that a user who reads the report after the fact can see that the analysis was performed with a stale bundle. `UPDATE-SIGN-REQ-027` requires that a bundle past its `fresh_until` date by more than two years be treated as `expired` rather than `stale`, and that an expired bundle be rejected for analysis with a `fatal` error stating the expiry date and the required action (obtain a fresh bundle). The two-year threshold is a design choice: it allows a reasonable grace period for an air-gapped environment while still bounding the period during which a bundle with a known-vulnerable schema can be used.

The freshness policy interacts with the revocation mechanism: a bundle that has been revoked is not merely stale, it is invalid, and the revocation section specifies how a user learns about a revocation without network access.

## Atomic activation and last-known-good bundle preservation

The activation of a new bundle is a transactional operation that either fully succeeds or fully fails, leaving the previous bundle in place. The transaction is implemented as a sequence of file system operations that are designed to be safe against interruption at any point.

The bundle store has the following layout: `bundle/` is the active bundle, `bundle.prev/` is the previous bundle (for rollback), `bundle.new/` is a staging directory for a new bundle being activated, `metadata.json` and `metadata.sha256` describe the active bundle, `transaction.log` records the last operation for recovery, and `trust/` contains the trust anchor. The activation procedure is: (1) write the new bundle to `bundle.new/`, (2) verify the new bundle (`KNOWLEDGE-REQ-062` through `KNOWLEDGE-REQ-064`), (3) write a `transaction.log` entry naming the new bundle and the operation, (4) atomically rename `bundle/` to `bundle.prev/` (replacing any existing `bundle.prev/`), (5) atomically rename `bundle.new/` to `bundle/`, (6) write the new `metadata.json` and `metadata.sha256`, (7) clear the `transaction.log` entry.

`UPDATE-SIGN-REQ-028` requires that steps (4) and (5) be atomic on the file system: the rename operation must be a single `rename(2)` call (or the platform equivalent) that either completes or fails, never partially completes. `UPDATE-SIGN-REQ-029` requires that the `transaction.log` be written before the first rename and cleared after the last rename, so that a crash between steps leaves a recoverable state. `UPDATE-SIGN-REQ-030` requires that the loader detect an incomplete transaction at startup (a `transaction.log` entry that was not cleared) and complete the transaction if it can determine that the new bundle was fully written and verified, or roll back to `bundle.prev/` if it cannot. The recovery is described in `FAIL-RECOVERY-001` and is automatic.

`UPDATE-SIGN-REQ-031` requires that the previous bundle be preserved in `bundle.prev/` for at least one activation cycle, so that rollback is possible. `UPDATE-SIGN-REQ-032` requires that a second activation overwrite `bundle.prev/` with the newly-previous bundle, so that `bundle.prev/` always contains the bundle that was active before the current one. `UPDATE-SIGN-REQ-033` requires that the `bundle rollback` command restore `bundle.prev/` to `bundle/` after verifying it, and that the rollback itself be transactional (using the same steps but in reverse) so that a crash during rollback leaves a recoverable state.

The last-known-good preservation extends beyond the immediate previous bundle: the `bundle-store/known-good/` directory contains a copy of the most recent bundle that passed a full analysis without any internal errors, updated on each successful analysis. If the active bundle is found to be corrupt at load time and `bundle.prev/` is also unusable, the loader falls back to `known-good/` and reports the fallback with a `warning`. `UPDATE-SIGN-REQ-034` requires this fallback and `UPDATE-SIGN-REQ-035` requires that the known-good copy be signed and verified on use, so that a corrupted known-good copy is detected rather than silently used.

## Interrupted updates and crash recovery

The crash recovery mechanism is a corollary of the transactional activation and is specified in the failure-handling document (`FAIL-RECOVERY-001` through `FAIL-RECOVERY-003`). The update mechanism's specific contribution is the `transaction.log` format and the recovery actions it enables.

`UPDATE-SIGN-REQ-036` requires that the `transaction.log` be a single-line JSON document with fields `operation` (one of `activate`, `rollback`, `import`, `delete`), `bundle_id`, `bundle_version`, `stage` (one of `staged`, `verified`, `renamed-prev`, `renamed-new`, `metadata-written`), and `timestamp`. The log is written before each stage transition and is cleared (truncated to zero bytes) after the final stage.

`UPDATE-SIGN-REQ-037` requires that the loader, at startup, read the `transaction.log` if it exists and perform recovery based on the `stage`. A `stage` of `staged` means the new bundle was written but not verified; the loader deletes `bundle.new/` and clears the log. A `stage` of `verified` means the new bundle was verified but not yet renamed; the loader can complete the activation (rename to `bundle/` after renaming `bundle/` to `bundle.prev/`) or roll back (delete `bundle.new/`), and the choice depends on whether the operation was user-initiated or automatic. The loader defaults to rollback for safety. A `stage` of `renamed-prev` means `bundle/` was renamed to `bundle.prev/` but the new bundle was not yet renamed; the loader renames `bundle.prev/` back to `bundle/` and deletes `bundle.new/`. A `stage` of `renamed-new` means both renames completed but the metadata was not written; the loader writes the metadata from `bundle.new/`'s manifest and clears the log. A `stage` of `metadata-written` means the metadata was written but the log was not cleared; the loader clears the log.

`UPDATE-SIGN-REQ-038` requires that the recovery be logged with a `warning`-severity finding that names the recovered stage and the action taken, so that the user is informed that a crash occurred and how it was recovered. The recovery finding is included in the report header and in the `bundle info` output.

## Manual import/export through removable media

The manual import/export path is the air-gap mechanism. It allows a user to generate or obtain a bundle on a connected machine and transport it to an isolated machine without any network access on the isolated machine.

The export path on the connected machine is: the user runs `kubecheck bundle export <bundle-id> --output <path>` (or obtains the bundle from the official source), the command writes the bundle directory to `<path>` (or the bundle is downloaded to `<path>`), and the user packages the directory as a `.tar.gz` or `.zip` archive, computes the archive's checksum, and records both on the transfer document.

The import path on the isolated machine is: the user copies the archive and the checksum to the isolated machine, verifies the archive's checksum against the recorded value, extracts the archive to a staging directory, and runs `kubecheck bundle import --from-dir <staging>` (or `kubecheck bundle activate --from-dir <staging>`). The import command runs the five validation stages (`KNOWLEDGE-REQ-060` through `KNOWLEDGE-REQ-064`), verifies the bundle's `bundle_version` against the active bundle's `bundle_version` (`UPDATE-SIGN-REQ-020`), verifies the freshness policy (`UPDATE-SIGN-REQ-024`), and activates the bundle transactionally (`UPDATE-SIGN-REQ-028` through `UPDATE-SIGN-REQ-033`).

`UPDATE-SIGN-REQ-039` requires that the import path not require network access at any point. `UPDATE-SIGN-REQ-040` requires that the import path accept the same bundle format as the online path, so that a bundle generated for online use can be transported for offline use without modification. `UPDATE-SIGN-REQ-041` requires that the import path accept a bundle whose signature was produced offline (the signing can be done on an air-gapped signing host, with the bundle directory transported to the host, signed, and transported back).

`UPDATE-SIGN-REQ-042` requires that the user be able to verify the imported bundle's provenance through `kubecheck bundle info <bundle-id> --show-provenance`, which displays the bundle's ID, version, signer, generation timestamp, source commit, provenance list, and freshness status. The output is intended to be included in the user's audit records so that a security reviewer can see exactly what was imported and from where.

The removable-media transport has one specific risk that the document addresses: **media substitution**. An attacker who has physical access to the media could substitute a different bundle between the connected machine and the isolated machine. The signature verification after import is the defense: a substituted bundle either has a valid signature (which requires the attacker to have the release key, which is not on the media) or is rejected. `UPDATE-SIGN-REQ-043` requires that the user be informed that the transport media is untrusted and that the signature verification is the security mechanism, not the media's physical custody.

## Revocation and emergency replacement of compromised bundles

The revocation mechanism handles the case where a bundle is discovered to be malicious or defective after it has been activated. The mechanism has two components: the revocation list and the emergency replacement procedure.

The revocation list is a signed document (`revocations.json`) that names revoked bundles by their `bundle_id` and `bundle_version`. The list is published by the project alongside each release, and it is included in each new bundle so that a user who updates to a new bundle also receives the revocations that preceded it. `UPDATE-SIGN-REQ-044` requires that the revocation list be signed by the same release key that signs bundles, and that the loader verify the signature before applying the list.

`UPDATE-SIGN-REQ-045` requires that the loader apply the revocation list to the active bundle at load time: if the active bundle's `bundle_id` and `bundle_version` are in the revocation list, the loader refuses to use the bundle and reports the revocation with a `fatal` error naming the revocation reason and the recommended replacement. The loader also applies the list to `bundle.prev/` and to `known-good/`, so that a revoked bundle cannot be used via any of the fallback paths.

The revocation list is delivered as part of a new bundle, so a user who has not received a new bundle is not aware of the revocation. This is a limitation of the offline mechanism and it is documented explicitly. `UPDATE-SIGN-REQ-046` requires that the user-facing documentation state that revocation awareness requires updating to a new bundle, and that an air-gapped user with a stale bundle may be using a revoked bundle without knowing it. The mitigation is the freshness policy: a bundle that is far past its `fresh_until` date is `expired` and is rejected, which bounds the period during which a revoked bundle can be used.

The emergency replacement procedure for a compromised signing key is: the project publishes a new engine release whose release key set excludes the compromised key; the project publishes a revocation list that revokes every bundle signed by the compromised key; the project publishes new bundles signed by a fresh key. Users who update their engine receive the new key set and the revocation list, and the loader rejects the compromised bundles. Users who do not update their engine remain vulnerable, and the project's only defense is the announcement (via the security advisory, the release notes, and the project's website). `UPDATE-SIGN-REQ-047` requires that the security advisory state the compromise, the affected bundles, the fixed engine version, and the required user action, and that the advisory be published within the same timeframe as the incident response procedure's disclosure phase (`THREAT-REQ-016`).

The emergency replacement of a compromised bundle (not key) is simpler: the project publishes a revocation list entry for the bundle and a replacement bundle signed by a valid key. Users who update receive the revocation and the replacement; users who do not update may continue to use the compromised bundle. The compromise's severity determines the project's response: a bundle with a defective rule (a false negative) is a correctness issue; a bundle with a malicious rule (a false negative deliberately introduced) is a security issue; both are handled through the revocation mechanism, but the latter is treated with the incident-response urgency.

## Update provenance and audit logs

Every update operation produces an audit log entry. The audit log is a local file (`bundle-store/audit.log`) that records, in JSON Lines format, every activation, rollback, import, export, delete, and purge operation with the operation type, the bundle ID, the bundle version, the signer, the timestamp, the user (from the platform's user identity, read only for the audit entry — the tool otherwise does not read user identity, see `DATA-010`), and the outcome (success or failure with a reason).

`UPDATE-SIGN-REQ-048` requires that the audit log be append-only, that entries not be modified or deleted except by the `bundle purge` operation (which deletes the entire store), and that the log be readable via `kubecheck bundle audit` with filtering by bundle ID, operation type, and date range. `UPDATE-SIGN-REQ-049` requires that the audit log entry be emitted before the operation completes (so that a crash during the operation leaves a record of what was attempted) and updated with the outcome after the operation completes. `UPDATE-SIGN-REQ-050` requires that the audit log be included in the `support-bundle` command's output (`PRIVACY-REQ-035`) so that a user can share it with the project for troubleshooting, and that the log contain no manifest content (it records bundle operations, not analysis, so it does not touch manifest data).

The audit log is the mechanism by which a security reviewer can reconstruct the history of a KubeCheck installation: which bundles were activated, when, by whom, whether any were revoked, and whether any recovery occurred. `UPDATE-SIGN-REQ-051` requires that the log be retained for at least the lifetime of the installation (i.e., until `bundle purge`), so that the history is available for the audit period required by the user's organization. `UPDATE-SIGN-REQ-052` requires that the log be protected by the store's restrictive permissions and that its integrity be checkable by the user (`kubecheck bundle audit --verify` recomputes a hash chain over the log entries and reports any discrepancy).

## No mandatory network access

The update mechanism has both an online path and an offline path. The online path is `kubecheck bundle update`, which contacts the configured update source and downloads a bundle. The offline path is `kubecheck bundle import --from-dir` or `kubecheck bundle activate --from-dir`, which reads a bundle from a local directory with no network access. Both paths perform the same verification, the same compatibility checks, and the same transactional activation.

`UPDATE-SIGN-REQ-053` requires that the offline path be usable without any network access, that it not attempt any network connection as part of its operation, and that it not require any online service to complete. `UPDATE-SIGN-REQ-054` requires that the default configuration of the tool not require network access, and that the `analyze` command continue to work with the last-activated bundle regardless of network state. `UPDATE-SIGN-REQ-055` requires that the online path be opt-in (the user must run a command that explicitly names the update operation), and that no automatic update check occur in the background (`PRIVACY-REQ-037`).

The offline path's security comes entirely from the signature verification against the local trust anchor. An air-gapped user with a fresh bundle and a valid signature has the same security assurance as a connected user who downloaded the bundle over HTTPS, because the signature is the security mechanism in both cases; the HTTPS transport in the online path protects against network corruption, not against a compromised server, and the signature is the defense against the latter.

## Failure behavior and clear user messaging

The update mechanism has eight failure modes, each with a specific user-visible message, a specific exit code, and a specific recovery action. The failure modes are:

`UPDATE-FAIL-001` is a **checksum mismatch on the transport archive**. The message names the archive path, the expected checksum, and the actual checksum. The exit code is non-zero. The recovery is to re-transfer the archive or to re-compute the checksum. The test is `UPDATE-SIGN-TEST-001`.

`UPDATE-FAIL-002` is a **signature verification failure**. The message names the bundle ID, the signer, and the failure reason (invalid signature, unknown key, expired key, revoked key). The exit code is non-zero. The recovery is to verify the bundle's source and, if the source is trusted, to report the failure. The test is `UPDATE-SIGN-TEST-002`.

`UPDATE-FAIL-003` is a **compatibility failure**. The message names the failed check (format version, engine range, Kubernetes version coverage) and the values involved. The exit code is non-zero. The recovery is to obtain a compatible bundle or to upgrade the engine. The test is `UPDATE-SIGN-TEST-003`.

`UPDATE-FAIL-004` is a **rollback attempt**. The message names the active bundle's version, the incoming bundle's version, and the signer. The exit code is non-zero. The recovery is to use the active bundle or a newer one. The test is `UPDATE-SIGN-TEST-004`.

`UPDATE-FAIL-005` is a **revoked bundle**. The message names the revoked bundle and the revocation reason. The exit code is non-zero. The recovery is to obtain the replacement bundle named in the revocation entry. The test is `UPDATE-SIGN-TEST-005`.

`UPDATE-FAIL-006` is an **expired bundle**. The message names the bundle and the expiry date. The exit code is non-zero. The recovery is to obtain a fresh bundle. The test is `UPDATE-SIGN-TEST-006`.

`UPDATE-FAIL-007` is a **crash-during-activation recovery**. The message states that the previous activation was interrupted, what stage was recovered, and what action was taken. The exit code is the analysis exit code (the recovery succeeds and analysis proceeds). The test is `UPDATE-SIGN-TEST-007`.

`UPDATE-FAIL-008` is a **trust anchor failure** (the trust anchor is missing, malformed, or has a root signature that does not verify). The message names the trust anchor file and the failure. The exit code is non-zero. The recovery is to reinstall the engine (which restores the trust anchor) or to restore the trust anchor from a known-good backup. The test is `UPDATE-SIGN-TEST-008`.

`UPDATE-SIGN-REQ-056` requires that every failure message name the specific failure, the values involved, and the recovery action, without ambiguity. A message that says "bundle verification failed" without naming the reason is a defect in the tool's error reporting, not a legitimate failure message. `UPDATE-SIGN-REQ-057` requires that the exit codes follow `docs/cli/EXIT_CODE_CONTRACT.md` and be identical across the online and offline paths.

## Cryptographic verification workflow and key-management boundaries

The complete verification workflow, from archive receipt to active bundle, has nine steps.

**Step 1: Verify the transport archive checksum.** The user (or a wrapper script) computes the SHA-256 of the archive and compares it against the published checksum. This detects transport corruption. **Step 2: Extract the archive safely.** The extraction uses the archive-safety rules from `SEC-YAML-REQ-027` (no path traversal, no absolute paths, no symlinks, no device files). **Step 3: Read the manifest.** The loader parses `manifest.json` and validates it against the manifest schema. **Step 4: Check the format and engine compatibility.** The loader checks the format version, the engine compatibility range, and the Kubernetes version coverage. **Step 5: Verify the file hashes.** The loader computes the SHA-256 of every listed file and compares it against the manifest's `files` list. A mismatch is a corruption or tampering detection. **Step 6: Verify the signature.** The loader computes the canonical serialization, verifies the signature against the release key set, and verifies that the release key's signature by the root key is present in the trust anchor. **Step 7: Apply the revocation list.** The loader checks the active bundle's ID and version against the revocation list embedded in the incoming bundle, and rejects the incoming bundle if either the incoming or the active bundle is revoked. **Step 8: Check the version ordering.** The loader compares the incoming `bundle_version` against the active `bundle_version` and rejects a rollback attempt. **Step 9: Activate transactionally.** The loader performs the transactional activation described above.

`UPDATE-SIGN-REQ-058` requires that the workflow be performed in this order and that a failure at any step prevent the later steps from running. `UPDATE-SIGN-REQ-059` requires that the workflow's steps be logged in the audit log so that a security reviewer can see which step failed if a bundle is rejected.

The key-management boundaries are: the private root key is held in an offline HSM and is used only to sign release keys; the private release keys are held in a signing service with multi-party approval and are used to sign bundles and revocation lists; the public root key is embedded in the engine and distributed via the engine's install channel; the public release keys are distributed via the engine's install channel and via the bundle's signature metadata; the user's trust anchor is created at install time and is not modified by the update mechanism.

`UPDATE-SIGN-REQ-060` requires that the signing service never expose the private key to the build pipeline, that signing requests be authenticated and authorized, and that the signing service log every signing operation with the bundle ID, the requester, and the timestamp. `UPDATE-SIGN-REQ-061` requires that the signing ceremony be documented in `docs/distribution/SIGNING_CEREMONY.md` and that the ceremony's steps be reviewed by the Security Architecture owner before any key is used in production. `UPDATE-SIGN-REQ-062` requires that the signing service's logs be retained for at least the lifetime of the key and be available for audit.

## Test vectors using non-production example keys

The document includes test vectors with non-production example keys so that the verification implementation can be tested without access to the production keys. The test vectors use the Ed25519 key pair whose private key is the 32-byte value `0x00...00` followed by `0x01` (a well-known test key documented in RFC 8032 §7.1) and whose public key is `0x3b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29`. These keys are publicly known and must not be used for any production signing; their only purpose is to provide reproducible test cases.

`TEST-VECTOR-001` is the signature of the empty message under the test key. `TEST-VECTOR-002` is the signature of `b"kubecheck-bundle-test"` under the test key. `TEST-VECTOR-003` is a minimal valid bundle manifest signed by the test key, with the `signature.value` field populated with the expected signature. `TEST-VECTOR-004` is the same manifest with one field modified (the `bundle_version`), demonstrating that the signature does not verify. `TEST-VECTOR-005` is the canonical serialization of `TEST-VECTOR-003`'s authenticated fields, provided so that an implementation can reproduce the serialization byte-for-byte.

`UPDATE-SIGN-REQ-063` requires that the test vectors be checked into the repository at `testdata/signatures/` and that the CI suite verify the implementation's signature generation and verification against them. `UPDATE-SIGN-REQ-064` requires that the test vectors be regenerated only when the signature scheme changes (a format-version bump) and that the regeneration be announced in the release notes.

## Open questions and unresolved decisions

Six open questions remain. `OPEN-UPDATE-01` asks whether the trust anchor should support a "pinned" mode in which the user explicitly pins a release key and the loader accepts only bundles signed by that key (this would allow an organization to freeze its bundle source, at the cost of not receiving future updates). `OPEN-UPDATE-02` asks whether the revocation list should be distributed via a separate small artifact that users can fetch without a full bundle, or only via bundles; the current design bundles it, which means a revocation reaches a user only when they update. `OPEN-UPDATE-03` asks whether the `bundle rollback` command should require the previous bundle to be within a freshness window, or whether rollback should be allowed regardless of the previous bundle's age. `OPEN-UPDATE-04` asks whether the audit log should use a hash chain (which the current design does) or a Merkle tree (which would allow inclusion proofs but is more complex). `OPEN-UPDATE-05` asks whether the signing service should support hardware tokens (which the current design allows) in addition to the multi-party approval workflow (which the current design requires), or whether one mechanism should be chosen as the default. `OPEN-UPDATE-06` asks whether the test vectors should be expanded to cover the full signature scheme (including key rotation and revocation list signing) or whether the five current vectors are sufficient.

This document is complete when twelve conditions hold. The trust model is stated with the three trust anchors and the two-level key hierarchy. The distinction between checksums (corruption detection) and signatures (authentication) is stated explicitly and the tool's output is required to distinguish them. The signing-key distribution mechanism is specified with the initial distribution and the rotation procedure. The digital signature scheme is specified with the authenticated metadata and the canonical serialization. The hash verification and archive integrity checks are specified with the archive-checksum-versus-internal-hash distinction. The compatibility checks are specified with the format, engine-range, and Kubernetes-version checks. The version ordering and anti-rollback controls are specified with the per-signer counter and the rejection behavior. The freshness policy and the offline exception are specified with the stale-versus-expired distinction. The atomic activation and last-known-good preservation are specified with the transactional layout and the recovery stages. The interrupted-update recovery is specified with the transaction log and the recovery actions. The manual import/export path is specified with the eight-step workflow and the media-substitution risk. The revocation and emergency replacement are specified with the signed revocation list and the key-compromise procedure. The update provenance and audit logs are specified with the audit log format and the hash chain. The no-mandatory-network guarantee is specified for both the online and offline paths. The failure behavior is specified with eight failure modes and their user-visible messages. The cryptographic verification workflow is specified with nine steps. The key-management boundaries are stated. The test vectors are specified with non-production example keys. The prohibition on hardcoding private keys is stated. Every requirement has a stable ID (`UPDATE-SIGN-REQ-NNN`), every key-management operation has a stable ID (`KEY-OP-NNN`), every failure has a stable ID (`UPDATE-FAIL-NNN`), and every test has a stable ID (`UPDATE-SIGN-TEST-NNN` and `TEST-VECTOR-NNN`). The document does not claim any implementation status, benchmark result, or verified detection rate, and it does not promise that any cryptographic primitive is unbreakable — it specifies the mechanisms, the boundaries, and the tests, and it leaves the assessment of cryptographic strength to the peer-reviewed primitives it uses.

The offline update and signing mechanism is the security foundation of the offline-first guarantee. A tool that claims to be offline-first but cannot verify its own knowledge updates is a tool that trades availability for trust; this document specifies how KubeCheck provides both, by making the bundle self-authenticating and the verification independent of any network service. The mechanism is designed for the air-gapped user first and the connected user second, because the connected user has the easier problem and the air-gapped user has the harder one, and a mechanism that works for the harder case works for both.
