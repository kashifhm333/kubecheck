# KubeCheck — Knowledge Build Pipeline

**Document ID:** KNOWLEDGE-BUILD-001 · **Status:** Normative — Approved · **Version:** 1.0.0 · **Owner:** Knowledge Engineering and CI/CD Architecture · **Last reviewed:** 2026-10-31

This document specifies the complete build pipeline that produces KubeCheck's schemas, rules, indexes, and release bundles. The pipeline is the mechanism by which authoritative upstream sources become the signed knowledge artifact that the offline CLI consumes, and it is the mechanism by which a change to a schema, a rule, or a lifecycle entry is traced back to its source, verified against its tests, validated against the benchmark corpus, and certified as safe to distribute. The pipeline exists because a knowledge bundle is not a file — it is a claim. The claim is that every schema in the bundle corresponds to the Kubernetes release it cites, that every rule is what the bundle says it is, that every lifecycle entry reflects the upstream deprecation policy, that the bundle is reproducible from its recorded inputs, and that the bundle has not been tampered with. The pipeline is the set of stages that turn each of those claims into an artifact that the offline loader can verify, and it is the set of gates that prevent a bundle that fails any claim from ever being published.

Every requirement in this document is identified with the prefix `BUILD-REQ-NNN`, every pipeline stage with `STAGE-<NAME>-NNN`, every gate with `GATE-BUILD-NNN`, and every test with `BUILD-TEST-NNN`. The document is written to be read continuously, because the pipeline is a sequence in which each stage depends on the outputs of the previous stage and the gate at the end of each stage is the mechanism by which a defect discovered at that stage is prevented from propagating to the next. The central architectural constraint — the constraint the entire pipeline is designed around — is that **the connected build pipeline must never become a runtime dependency for the offline CLI**. The pipeline runs on connected infrastructure; the CLI runs on the user's machine, frequently an air-gapped machine. Every dependency the pipeline introduces is confined to the pipeline; the CLI's runtime dependencies are the runtime dependencies specified in the engine's dependency manifest, and the pipeline's dependencies are the pipeline's own. A change to the pipeline that would make the CLI require a network service, a build-time artifact, or a pipeline-generated file at runtime is a violation of the offline guarantee and must be rejected at the architecture-review stage.

## The governing principles

Five principles govern the pipeline, and every stage and gate derives from them.

The first principle, `BUILD-REQ-001`, is **deterministic generation**. Given the same source commit, the same generator version, the same pinned dependency set, and the same build environment, the pipeline produces byte-identical outputs (modulo the documented non-deterministic metadata — the generation timestamp, and any cryptographic nonce introduced by the signing service). The determinism is the property that makes reproducibility possible, and reproducibility is the property that makes auditability possible: a third party who has the recorded inputs can re-run the pipeline and compare the output byte-for-byte, which is the only way to prove that the pipeline actually did what it claims to have done.

The second principle, `BUILD-REQ-002`, is **pinned sources**. Every input to the pipeline is pinned to an exact version or commit. The Kubernetes source is pinned to a release tag and a commit hash; the YAML specification is pinned to a revision; the rule schema is pinned to a version; the dependency set is pinned to a lockfile; the generator toolchain is pinned to an image digest. An unpinned input is an input that can change without the pipeline noticing, and an input that can change without the pipeline noticing is an input that can introduce a regression that the pipeline's tests did not catch. Pinning is not a limitation; it is the mechanism by which the pipeline's output is a function of its declared inputs.

The third principle, `BUILD-REQ-003`, is **provenance by construction**. Every schema, every rule, every lifecycle entry, every feature-gate entry, and every catalog entry in the bundle records the source it was derived from, the source's version, the retrieval date, and — where the source is a file or a deterministic document — a content hash. The provenance is not a documentation exercise; it is a machine-checkable field that the bundle verifier reads, and the release gate `GATE-BUILD-005` blocks a bundle whose provenance is incomplete or whose source hashes do not match the source that the pipeline actually fetched.

The fourth principle, `BUILD-REQ-004`, is **fail-closed**. A stage that cannot complete its validation does not produce a partial output; it fails the pipeline and reports the specific failure. A rule that fails schema validation is not "included with a warning"; it is rejected and the pipeline stops. A schema that fails to extract is not "skipped"; it is a missing schema for a covered GVK and the pipeline stops. A bundle whose signature fails verification is not "published with a note"; it is not published. The fail-closed principle is the mechanism by which a defective bundle never reaches a user who trusts the tool.

The fifth principle, `BUILD-REQ-005`, is **isolation between the pipeline and the runtime**. The pipeline's build environment is isolated from the pipeline's output. The CLI does not read the pipeline's intermediate files, does not depend on the pipeline's container images, does not require the pipeline's signing service at runtime, and does not have any runtime dependency on the pipeline's network services. A bundle that a user installs is a self-contained artifact that the CLI verifies against its own trust anchor and uses without contacting the pipeline. The pipeline's only runtime artifact is the bundle it publishes, and the bundle is signed and self-sufficient.

These five principles interact to give the pipeline its essential property: the pipeline produces a signed, versioned, provenance-complete, reproducible artifact that the CLI can verify and use on a machine that has never been connected to the pipeline, and the pipeline's defects cannot reach the CLI because every defect is caught at a stage gate before the artifact is published.

## Pipeline overview

The pipeline has fourteen stages, organized into four phases. The first phase is **acquisition**, in which the pipeline fetches the authoritative sources and verifies their identity. The second phase is **generation**, in which the pipeline extracts the schemas, normalizes them, and produces the intermediate artifacts. The third phase is **validation**, in which the pipeline runs every test, benchmark, and gate. The fourth phase is **publication**, in which the pipeline signs the bundle, publishes it, and records its provenance. The fourteen stages are:

**Acquisition phase.** `STAGE-SOURCE-FETCH-001` fetches the pinned Kubernetes source; `STAGE-SOURCE-VERIFY-002` verifies the source's commit hash and tag; `STAGE-PROVENANCE-COLLECT-003` collects the provenance metadata for every source; `STAGE-LICENSE-COLLECT-004` collects the license texts.

**Generation phase.** `STAGE-SCHEMA-EXTRACT-005` extracts the OpenAPI schemas from the Kubernetes source; `STAGE-SCHEMA-NORMALIZE-006` normalizes the schemas into the bundle's schema format; `STAGE-RULE-VALIDATE-007` validates the authored rules against the rule schema; `STAGE-LIFECYCLE-MERGE-008` merges the lifecycle metadata from the deprecation guide; `STAGE-FEATURE-GATE-MERGE-009` merges the feature-gate metadata; `STAGE-INDEX-BUILD-010` builds the schema, rule, and catalog indexes.

**Validation phase.** `STAGE-STATIC-CHECK-011` runs the static checks on every artifact; `STAGE-UNIT-TEST-012` runs the unit tests for every rule and schema; `STAGE-REGRESSION-TEST-013` runs the regression corpus; `STAGE-FUZZ-014` runs the fuzz corpus; `STAGE-COMPAT-TEST-015` runs the compatibility matrix; `STAGE-BENCHMARK-016` runs the false-positive and accuracy benchmark.

**Publication phase.** `STAGE-BUNDLE-ASSEMBLE-017` assembles the bundle directory from the validated artifacts; `STAGE-BUNDLE-VERIFY-018` verifies the assembled bundle end-to-end; `STAGE-BUNDLE-SIGN-019` signs the bundle; `STAGE-ARTIFACT-PUBLISH-020` publishes the archive and metadata; `STAGE-RELEASE-METADATA-021` records the release metadata; `STAGE-AUDIT-LOG-022` appends the pipeline's audit log.

A stage that produces an output for the next stage is a **producer**, and a stage that consumes an output is a **consumer**. The pipeline's dependency graph is a directed acyclic graph with no cycles; the pipeline's scheduler respects the graph and does not start a consumer before its producer has completed. `BUILD-REQ-006` requires that the dependency graph be declared in a machine-readable file (`pipeline/dag.yaml`) and that the scheduler reject a pipeline definition whose graph is not acyclic or whose stage has an undeclared dependency.

## Authoritative source acquisition and pinned source versions

The acquisition phase fetches the sources that the generation phase derives knowledge from. The sources are pinned to exact versions, and the pinning is the mechanism by which a source change is intentional rather than accidental.

The primary source is the **Kubernetes source tree**, pinned to a release tag (for example `v1.34.2`). The source is fetched from the official Kubernetes GitHub repository, and the fetch is verified against two independent values: the tag's annotated tag object (which GitHub signs for release tags) and the commit hash of the release branch at the tag's date. The verification ensures that the fetched source is the source the Kubernetes project published for that release, not a source that an attacker substituted by compromising the mirror or by redirecting the fetch.

`STAGE-SOURCE-FETCH-001` performs the fetch. Its input is the release tag list (from the pipeline's configuration); its output is a checked-out source tree at each tag. Its validation rules are: the source tree must be a git repository, the tag must exist, the tag must be an annotated tag (not a lightweight tag), and the working tree must be clean. Its failure conditions are: the fetch fails, the tag does not exist, the tag is a lightweight tag, or the working tree is dirty. Its output artefact is a source manifest that records, for each tag, the full commit hash, the tag's annotation, and the commit's signature status.

`STAGE-SOURCE-VERIFY-002` verifies the source's identity. Its input is the source manifest from `STAGE-SOURCE-FETCH-001`; its output is a verified source manifest. Its validation rules are: the commit hash matches the value recorded in the source manifest, the tag's annotation is present, and the tag's date is within the documented release window. Its failure conditions are: any of the above checks fail. Its output is written to `pipeline/sources/<tag>.json` and is used by every later stage that needs to know which source the pipeline actually used.

`BUILD-REQ-007` requires that the source manifest record, for each Kubernetes release tag: the tag name, the annotated tag object hash, the commit hash, the commit's author and committer dates, the commit's GPG signature status (Kubernetes releases are signed by the release manager), and the SHA-256 of the source tree's `go.mod` file (which is a stable fingerprint of the module's dependency set at that commit). The record is the pipeline's claim about which source it used, and the claim is verifiable by a third party who fetches the same tag and compares the values.

The secondary sources are the **Kubernetes Deprecated API Migration Guide** (for lifecycle metadata) and the **Kubernetes Feature Gates documentation** (for feature-gate metadata). These are documentation sources, not source code; they are fetched from the official Kubernetes website and pinned to a retrieval date, and the pipeline records the content hash of the page at retrieval time. The pinning is weaker than the source tree's pinning because the documentation pages are updated in place (there is no versioned tag for a documentation page), but the content hash plus the retrieval date plus the page's version if available provides a record that a third party can reproduce by re-fetching the page on the same date or by consulting the page's version history.

`STAGE-PROVENANCE-COLLECT-003` collects the provenance metadata for every source. Its input is the verified source manifest and the fetched documentation pages; its output is the provenance list that will appear in the bundle's manifest. Its validation rules are: every source has a `source_id`, a `source_type`, a `source_version` (the tag or retrieval date), a `retrieved_at` date, and a `content_hash` where the source is a file or a deterministic document. Its failure conditions are: any source lacks a required field, any content hash does not match the re-computed hash, or any source's URL is not reachable (for documentation sources) or is not a pinned tag (for source trees). Its output is written to `pipeline/provenance.json` and is included in the bundle's manifest by `STAGE-BUNDLE-ASSEMBLE-017`.

`STAGE-LICENSE-COLLECT-004` collects the license texts for every source and every dependency. Its input is the source manifest and the dependency manifest; its output is the `LICENSES/` directory that will be included in the bundle. Its validation rules are: every license declared by a dependency has a corresponding text file, every text file's SPDX identifier matches the declared identifier, and no license text is a placeholder. Its failure conditions are: a missing license text, a mismatched identifier, or a placeholder. Its output is written to `pipeline/licenses/` and is included in the bundle by `STAGE-BUNDLE-ASSEMBLE-017`.

`BUILD-REQ-008` requires that every source be pinned to an exact version. A source that is fetched from a `latest` URL or a moving branch is not acceptable. A source that is fetched from a mirror is acceptable only if the mirror is verified against the upstream's tag object or commit hash, and the verification is recorded in the source manifest.

## Kubernetes OpenAPI schema extraction and normalization

The schema extraction stage is the largest stage in the pipeline and the one most directly tied to the Kubernetes release. Kubernetes publishes its OpenAPI schemas through the `kube-openapi` generator, which produces a per-version OpenAPI v3 document from the API packages in the source tree. The pipeline runs the generator against the pinned source tree and extracts the per-GVK schemas from the output.

`STAGE-SCHEMA-EXTRACT-005` performs the extraction. Its input is the verified source tree; its output is a set of per-GVK OpenAPI schemas, one per covered GVK per covered Kubernetes version. Its validation rules are: the generator completes without error, the generated document parses as valid OpenAPI v3, every GVK in the document has a schema, and every schema has the required fields (`type`, `properties` or `allOf`, `description`). Its failure conditions are: the generator fails, the document does not parse, a GVK is missing a schema, or a schema is missing a required field. Its output is written to `pipeline/schemas/raw/<version>/` and is used by `STAGE-SCHEMA-NORMALIZE-006`.

The generator runs inside a pinned container image (the image digest is recorded in the pipeline configuration and is the same across all platform builds). The container is built from the same source tree as the engine (or from a pinned toolchain image, depending on the project's build strategy), and the container's `go.sum` (or equivalent) is recorded in the source manifest. `BUILD-REQ-009` requires that the generator image be pinned to an exact digest and that the digest be recorded in the source manifest.

`STAGE-SCHEMA-NORMALIZE-006` normalizes the extracted schemas into the bundle's schema format. Its input is the raw schemas; its output is the normalized per-GVK schema files that will appear in the bundle. Its validation rules are: the normalization is deterministic (a second run produces byte-identical output), the normalization preserves every schema constraint (`type`, `required`, `enum`, `pattern`, `minimum`, `maximum`, `format`, `additionalProperties`), and the normalization preserves the schema's provenance reference. Its failure conditions are: the normalization changes a schema's meaning, drops a constraint, or cannot find a provenance reference for a schema. Its output is written to `pipeline/schemas/normalized/<version>/` and is used by `STAGE-INDEX-BUILD-010`.

The normalization step is where the pipeline's version-aware behavior is implemented. `BUILD-REQ-010` requires that every schema be normalized for a specific Kubernetes version, that the normalized schema's `gvk` field match the version's `apiVersion`, and that the normalized schema be assigned to exactly one version. A schema that appears in two versions is fine (the same GVK exists in both versions), but each version's schema is a separate normalized file; there is no "shared" schema that is used for multiple versions, because the schema for a GVK can differ between versions and the bundle must select the version-specific schema at load time.

The schema extraction and normalization also produce the schema index, which `STAGE-INDEX-BUILD-010` finalizes. `BUILD-REQ-011` requires that the schema index list every normalized schema with its GVK, its hash, and its size, and that the index itself be included in the bundle's `files` list. The index is what the offline loader reads first, so that it can build the in-memory lookup without reading every schema file.

## Rule authoring and schema validation

The rule pack is the bundle's behavioral component. The rules are authored by the project's rule authors, who write them as YAML files in the rule format specified in `DIAGNOSTIC_RULE_SPEC.md`, and the pipeline validates every rule against the rule schema before the rule enters a bundle.

`STAGE-RULE-VALIDATE-007` performs the validation. Its input is the authored rule pack directory (`rules/<pack-id>/` in the project repository); its output is a validated rule pack directory. Its validation rules are: every rule parses as valid YAML, every rule validates against the rule schema (a JSON Schema document, `schema/rule-1.0.0.json`, shipped with the engine), every rule's `id` is unique within the pack and the bundle, every rule's `metadata.category` is one of the categories in the taxonomy, every rule's `metadata.evidence_class` is compatible with its `metadata.severity`, every rule's `applicability` matches the schemas that the rule will be evaluated against, every rule's fixtures are present, and every rule's fixtures pass when the rule is evaluated against them. Its failure conditions are: any of the above checks fail. Its output is written to `pipeline/rules/validated/` and is used by `STAGE-BUNDLE-ASSEMBLE-017`.

The rule validation includes the **fixture execution** step, which is the rule's unit test. `BUILD-REQ-012` requires that every rule's positive, negative, and boundary fixtures be executed at validation time and that every fixture produce the expected result. A rule whose positive fixture does not trigger the rule, whose negative fixture does trigger it, or whose boundary fixture produces an unexpected result is rejected. The rejection is a gate failure and blocks the bundle.

The rule validation also includes the **cross-reference check**, which verifies that every rule's `dependencies` field references a rule that exists in the bundle, that every rule's `applicability.kinds` references a GVK that exists in the schema index, and that every rule's `evidence` binding references a field that exists in the schema for the rule's applicable GVKs. `BUILD-REQ-013` requires these checks; a rule whose dependency, kind, or evidence path does not resolve is rejected.

## Provenance and license verification

The provenance and license verification is a gate that blocks a bundle whose knowledge cannot be traced to a source. It is performed at `STAGE-PROVENANCE-COLLECT-003` for the sources and at `STAGE-BUNDLE-VERIFY-018` for the assembled bundle.

The source provenance gate checks that every source in the provenance list has a stable identifier, a version, a retrieval date, and a content hash (for file or deterministic-document sources), and that the hash matches the recomputed hash of the source. `BUILD-REQ-014` requires this gate; a source whose hash does not match is a source that changed between retrieval and verification, and the bundle cannot be published.

The artifact provenance gate checks that every schema, rule, relationship definition, and catalog entry references at least one `source_id` from the provenance list, and that the `source_id` resolves to a source that passed the source provenance gate. `BUILD-REQ-015` requires this gate; an artifact without a provenance reference is an artifact whose derivation cannot be verified, and the bundle cannot be published.

The license gate checks that every bundled artifact is covered by a license whose text is present in the bundle's `LICENSES/` directory, and that the license is compatible with the project's license policy. `BUILD-REQ-016` requires this gate; a bundle that redistributes an artifact under a license whose text is missing, or under a license that is incompatible with the project's policy, cannot be published.

## Deterministic generation and reproducible outputs

The pipeline is deterministic: given the same inputs, it produces the same outputs. The determinism is enforced by three mechanisms: the pipeline's own code is deterministic (no timestamps in generated content, no random values, no iteration over unordered containers without sorting), the generator's behavior is deterministic (the `kube-openapi` generator produces the same output for the same input), and the environment is deterministic (the container image digest is pinned, the locale is fixed, the time zone is UTC, the file system ordering is sorted).

`BUILD-REQ-017` requires that the pipeline's output be byte-identical across two runs with the same inputs, except for the generation timestamp (which is recorded in the bundle manifest and is the only non-deterministic field) and the signature (which is deterministic for Ed25519 but is recorded separately). The determinism is verified by a reproducibility test that runs the pipeline twice and compares the outputs byte-for-byte.

The reproducibility test is `BUILD-TEST-001`. It runs the full pipeline on the pinned inputs, captures the output, then runs the pipeline again on the same inputs in a fresh container, and compares the two outputs. The test passes if the outputs are byte-identical except for the timestamp field; the test fails if any other difference is found. The test is run at every release and its result is recorded in the release notes. A release that fails the reproducibility test is not published.

`BUILD-REQ-018` requires that the reproducibility test be run on a third-party machine (or in a third-party environment) at least once per release, so that the reproducibility claim is not a self-attestation. The third-party run is the mechanism by which the project demonstrates that its reproducibility claim is not dependent on its own infrastructure.

## Duplicate detection and conflict handling

The pipeline detects and handles duplicates and conflicts in three places: duplicate rule IDs, duplicate schema GVKs, and conflicting lifecycle entries.

Duplicate rule IDs are detected by `STAGE-RULE-VALIDATE-007`. A rule ID that appears more than once in the same pack, or in two packs that are both included in the bundle, is a duplicate. The pipeline rejects the bundle with an error naming the two occurrences. `BUILD-REQ-019` requires this behavior; the rationale is that a duplicate rule ID would make the finding's `rule_id` ambiguous, and the rule metadata's semantics (evidence class, severity, remediation) are per-ID.

Duplicate schema GVKs are detected by `STAGE-SCHEMA-NORMALIZE-006`. A GVK that appears more than once for the same Kubernetes version is a duplicate. The pipeline rejects the bundle with an error naming the GVK and the two source schemas. `BUILD-REQ-020` requires this; the rationale is that the schema index maps a GVK to exactly one schema per version, and a duplicate would make the lookup ambiguous.

Conflicting lifecycle entries are detected by `STAGE-LIFECYCLE-MERGE-008`. A GVK whose lifecycle status differs between two sources (for example, the deprecation guide says "Deprecated in 1.32" and the API reference says "Removed in 1.32") is a conflict. The pipeline rejects the bundle with an error naming the GVK and the two entries, and the conflict is escalated to the Diagnostics Architecture owner for resolution. `BUILD-REQ-021` requires this; the rationale is that a lifecycle entry is a claim about the cluster's behavior, and a conflicting claim would produce inconsistent findings.

## Static checks, unit tests, regression tests, fuzzing, and compatibility tests

The validation phase runs five categories of tests, each of which is a gate that blocks the bundle if it fails.

`STAGE-STATIC-CHECK-011` runs the static checks: the rule schema validation, the schema format validation, the provenance reference check, the license coverage check, and the security policy checks (no network calls in the bundle's content, no shell commands, no secret-bearing values in remediation text). Its output is a static-check report; its failure conditions are any check that fails. `BUILD-REQ-022` requires the static checks to be run before the unit tests, so that a malformed artifact is caught before the tests attempt to use it.

`STAGE-UNIT-TEST-012` runs the unit tests: every rule's fixtures, every schema's validation tests, and the engine's own unit tests for the bundle-loading path. Its output is a unit-test report; its failure conditions are any test that fails. `BUILD-REQ-023` requires that the unit tests be run against the bundle that the pipeline just produced, not against a separate build, so that the tests exercise the exact artifact that will be published.

`STAGE-REGRESSION-TEST-013` runs the regression corpus: the set of manifests that the project has accumulated over its history, including every manifest that caused a regression when first introduced. Its output is a regression report; its failure conditions are any regression that is not a known, documented, and accepted regression. The regression corpus is versioned alongside the pipeline and is expanded whenever a new regression is discovered. `BUILD-REQ-024` requires the regression corpus to be a required part of the pipeline and a required gate.

`STAGE-FUZZ-014` runs the fuzz corpus against the bundle's parser and rule evaluator. Its output is a fuzz report; its failure conditions are any crash, hang, or memory-exhaustion event. The fuzz harness is described in `YAML_SECURITY_AND_PARSER_POLICY.md` §12 and is run at every release. `BUILD-REQ-025` requires the fuzz run to be at least one hour for every release, and to use the corpus accumulated from previous runs plus a fresh set of generated inputs.

`STAGE-COMPAT-TEST-015` runs the compatibility matrix: the bundle's behavior against every supported Kubernetes version, against the current and previous engine versions, and against the current and previous bundle format versions. Its output is a compatibility report; its failure conditions are any incompatibility that is not a documented and accepted limitation. `BUILD-REQ-026` requires the compatibility test to cover every version in the supported window and to assert that the bundle's behavior is identical across the engine versions that the bundle claims to support.

## False-positive evaluation and benchmark gates

The accuracy benchmark is the pipeline's final validation and the gate that determines whether the bundle's rules are trustworthy. The benchmark runs the bundle's rules against the benchmark corpus (the independently labelled corpus described in `ACCURACY_BENCHMARK_PROTOCOL.md`) and computes the per-category precision, recall, false-positive rate, and (for deterministic categories) observed true-positive rate with confidence intervals.

`STAGE-BENCHMARK-016` performs the benchmark. Its input is the bundle and the benchmark corpus; its output is a benchmark report. Its validation rules are: every deterministic category meets the precision target of ≥ 99% (`ACC-REQ-005`), every context-dependent category's false-positive rate does not exceed the documented threshold, and no category's metrics are lower than the previous release's metrics by more than the documented regression threshold. Its failure conditions are: any deterministic category below the precision target, any context-dependent category above the false-positive threshold, or any category whose metrics have regressed beyond the threshold.

The benchmark gate is `GATE-BUILD-007`. `BUILD-REQ-027` requires that `STAGE-BENCHMARK-016` run at every release and that a failure at any metric block the release. The gate's rationale is that a bundle is a claim about the tool's accuracy, and a bundle that does not meet the accuracy targets is a bundle that would produce false findings that the user would act on.

`BUILD-REQ-028` requires that the benchmark's results be recorded in the release notes, with the per-category metrics, the sample sizes, and the confidence intervals, so that a user can see the evidence that supports the bundle's accuracy claims. The release notes must state that the metrics are observations from the benchmark corpus, not probabilities for the user's specific environment.

## Bundle integrity and signing

The bundle assembly, verification, and signing are the final stages before publication. `STAGE-BUNDLE-ASSEMBLE-017` assembles the bundle directory from the validated artifacts: it copies the normalized schemas, the validated rules, the relationship definitions, the lifecycle metadata, the feature-gate metadata, the catalog, and the licenses into the bundle directory structure, and it generates the manifest with the file list, the hashes, the provenance, and the generation metadata. Its output is the assembled bundle directory. Its failure conditions are: any artifact missing, any file's hash not matching the manifest, or any field in the manifest not matching the pipeline's configuration.

`STAGE-BUNDLE-VERIFY-018` verifies the assembled bundle end-to-end: it runs the five validation stages from `KNOWLEDGE_BUNDLE_FORMAT.md` (`KNOWLEDGE-REQ-060` through `KNOWLEDGE-REQ-064`) against the assembled bundle, and it verifies the bundle's signature against a test key (the production signing happens later). Its output is a verification report. Its failure conditions are: any validation stage fails, or the signature does not verify. `BUILD-REQ-029` requires that the verification run against the exact bundle directory that will be signed, not against a copy, so that the verification covers every byte the signer will see.

`STAGE-BUNDLE-SIGN-019` signs the bundle. Its input is the verified bundle directory; its output is the signed bundle. Its validation rules are: the signing key is a release key whose public key is in the release key set, the signing key's validity period covers the release date, the signing service's authorization check passes (the release manager has approved the signing request), and the signature verifies against the public key. Its failure conditions are: the signing service rejects the request, the key is not authorized, or the signature does not verify. Its output is the signed bundle directory, and its audit log entry is appended to the project's signing audit log (`UPDATE-SIGN-REQ-060`). `BUILD-REQ-030` requires that the signing key be held by the signing service (not by the pipeline), that the pipeline authenticate to the signing service with a short-lived credential, and that the signing service log every signing request.

The signing stage is the pipeline's final opportunity to reject a defective bundle: a bundle that fails verification before signing is not signed, and a bundle that fails verification after signing is not published. `BUILD-REQ-031` requires that the post-signing verification be performed on the signed bundle, so that the signature itself is verified (not just the unsigned bundle's structure).

## Artifact publishing and release metadata

`STAGE-ARTIFACT-PUBLISH-020` publishes the signed bundle as a transport archive (`.tar.gz` and `.zip`) and a checksum file. Its input is the signed bundle directory; its output is the published artifacts. Its validation rules are: the archive's checksum matches the published checksum, the archive's contents match the bundle directory's contents, and the archive's permissions are world-readable. Its failure conditions are: the checksum mismatch, the contents mismatch, or the permissions are restrictive. Its output is published to the project's release artifact host and to the project's distribution channels. `BUILD-REQ-032` requires that the archive's checksum be published separately from the archive, so that a user who downloads the archive can verify it against a checksum obtained through an independent channel.

`STAGE-RELEASE-METADATA-021` records the release metadata: the bundle ID, the bundle version, the engine version, the Kubernetes version coverage, the signing key ID, the signature's fingerprint, the benchmark results, the regression test results, the compatibility matrix, and the release date. Its output is a release metadata JSON document (`releases/<bundle-id>.json`) that is published alongside the bundle and is included in the project's release notes. `BUILD-REQ-033` requires the release metadata to be the authoritative record of what the release contains, so that a user can verify the bundle's claims against a document that the project has published.

`STAGE-AUDIT-LOG-022` appends the pipeline's audit log entry: the pipeline run's identifier, the source commits, the generator version, the signing key, the release metadata, and the outcome. Its output is an audit log entry in the project's audit log (`pipeline/audit.log`), which is versioned alongside the repository. `BUILD-REQ-034` requires the audit log to be append-only and to be preserved for the lifetime of the project, so that a security reviewer can reconstruct the history of any bundle.

## Rollback, emergency fixes, and source updates

The pipeline supports three exceptional workflows: rollback of a published bundle, emergency fix of a published bundle, and source update for a new Kubernetes release.

**Rollback** is the process of reverting the active bundle to a previous version. It is not a pipeline operation (the pipeline does not publish an older bundle as a "new" release); it is a user-side operation (`kubecheck bundle rollback`) or an operator-side operation that publishes a new bundle with a higher `bundle_version` and a `rollback-to` metadata field that instructs the loader to use a specific earlier bundle's content. `BUILD-REQ-035` requires that a rollback bundle be generated through the same pipeline stages as a normal bundle, so that the rollback bundle is signed, verified, benchmarked, and audited, and that the rollback bundle's release metadata explicitly state which earlier bundle it reproduces.

**Emergency fix** is the process of publishing a new bundle to fix a security defect in a previously published bundle. The emergency fix follows the normal pipeline but with an expedited review: the Security Architecture owner approves the fix, the Diagnostics Architecture owner confirms the fix does not introduce a regression, and the benchmark is run in a reduced-scope mode (the affected category's tests, plus the regression corpus, plus the compatibility matrix) rather than in full-scope mode. `BUILD-REQ-036` requires that the emergency fix's release metadata state that it is an emergency fix, the defect it fixes, and the reduced-scope benchmark's results, so that the user understands the reduced verification.

**Source update** is the process of adding a new Kubernetes release to the bundle's coverage. The update follows the normal pipeline with the new release tag added to the source list. The pipeline fetches the new source, extracts the new schemas, merges the new lifecycle and feature-gate metadata, runs every test, and publishes a new bundle with the new release added and the oldest release (if the supported window is exceeded) moved to `deprecated` or removed. `BUILD-REQ-037` requires that the source update be announced in the release notes and that the new release's coverage be described in the compatibility matrix.

## Dependency pinning and isolated build environments

The pipeline's dependencies are pinned to exact versions, and the pipeline's build environment is isolated from the pipeline's runtime environment.

The pipeline's dependencies are recorded in a lockfile (`pipeline/requirements.lock` or the equivalent) that pins every dependency, its version, and its hash. The lockfile is committed to the repository and is updated only by a deliberate change that goes through the pipeline's own review process. `BUILD-REQ-038` requires the lockfile to be committed and to be used by every pipeline run; an unpinned dependency is a dependency that can change without the pipeline noticing.

The pipeline's build environment is a container image pinned to an exact digest. The image is built from a Dockerfile that pins every toolchain version (the compiler, the package manager, the signing client) and that does not include the pipeline's signing key. `BUILD-REQ-039` requires the build image digest to be recorded in the source manifest, so that a third party can reproduce the pipeline's environment byte-for-byte.

The pipeline's runtime environment (the CLI on the user's machine) is isolated from the build environment. The CLI's dependencies are the runtime dependencies specified in the engine's dependency manifest; they are not the pipeline's dependencies. The CLI does not import any pipeline code, does not read any pipeline file, and does not contact any pipeline service. `BUILD-REQ-040` requires that the CLI's dependency manifest and the pipeline's dependency manifest be distinct files with distinct lockfiles, so that a pipeline change cannot accidentally introduce a runtime dependency.

## Auditability and reproducibility

The pipeline's auditability rests on four artifacts: the source manifest, the provenance list, the release metadata, and the audit log. Together they allow a third party to reconstruct every claim the bundle makes and to reproduce the bundle from its inputs.

`BUILD-REQ-041` requires that the source manifest, the provenance list, the release metadata, and the audit log be published alongside the bundle, so that a user who installs the bundle can verify its claims. `BUILD-REQ-042` requires that the reproducibility test be run by a third party at least once per release and that the third-party result be published in the release notes, so that the reproducibility claim is not self-attested.

The pipeline's audit log is the mechanism by which a security reviewer can trace any bundle to its source and to the approvals that authorized its release. `BUILD-REQ-043` requires that the audit log include, for every release: the pipeline run's identifier, the source commits, the generator version, the signing key, the release manager's approval, the Security Architecture owner's approval (for emergency fixes), and the benchmark results. A release whose audit log entry is missing any of these fields is not a valid release, and the release process must reject it.

## The connected build pipeline never becomes a runtime dependency

The pipeline's most important architectural constraint is stated as `BUILD-REQ-044`: **the connected build pipeline must never become a runtime dependency for the offline CLI**. The constraint is enforced by the following rules.

The CLI's binary must not contain any pipeline code. `BUILD-REQ-045` requires that the CLI's binary be built from a source tree that does not include the pipeline's source; the pipeline's source lives in a separate directory (`pipeline/`) that is not compiled into the CLI. The CLI's binary must not import any pipeline package; the import-graph check at build time rejects any import that resolves to `pipeline/`.

The CLI's runtime must not require any pipeline service. `BUILD-REQ-046` requires that the CLI's runtime dependency graph include no network service, no build-time artifact, and no pipeline-generated file. The CLI's runtime dependencies are the engine's dependencies, the bundle store, and the OS. A change to the CLI that would introduce a pipeline service as a runtime dependency is a violation of `BUILD-REQ-044` and must be rejected at the architecture-review stage.

The bundle must be the only pipeline artifact that reaches the CLI. `BUILD-REQ-047` requires that the bundle be self-sufficient (it contains everything the CLI needs to analyze any manifest for any supported version), and that the CLI's loader not consult any pipeline service or any pipeline-generated file other than the bundle itself. A bundle that requires a pipeline service to be useful is not a bundle that satisfies the offline guarantee.

The release process must verify the constraint. `BUILD-REQ-048` requires a release gate (`GATE-BUILD-012`) that audits the CLI's binary for any pipeline reference, any network service, and any build-time artifact, and that fails the release if any is found. The gate's audit is performed by a static-analysis tool and by a network-namespace test that runs the CLI's full acceptance suite on a network-isolated machine.

## Pipeline stages, gates, and the definition of done

The pipeline has fourteen stages, each of which has an input, an output, a set of validation rules, a set of failure conditions, and a gate that blocks the pipeline if the validation fails. The stages are organized into four phases as described above, and the gates are:

`GATE-BUILD-001` (source verification) blocks if any source's commit hash or tag object does not match the pinned value. `GATE-BUILD-002` (provenance completeness) blocks if any source or artifact lacks a complete provenance record. `GATE-BUILD-003` (license coverage) blocks if any bundled artifact's license text is missing or incompatible. `GATE-BUILD-004` (schema completeness) blocks if any covered GVK for any covered Kubernetes version lacks a schema. `GATE-BUILD-005` (rule validation) blocks if any rule fails schema validation or fixture execution. `GATE-BUILD-006` (regression and fuzz) blocks if any regression test or fuzz run fails. `GATE-BUILD-007` (benchmark) blocks if any category fails its precision or false-positive target. `GATE-BUILD-008` (compatibility) blocks if any version in the supported window is incompatible with the bundle. `GATE-BUILD-009` (determinism) blocks if two pipeline runs produce different outputs. `GATE-BUILD-010` (bundle verification) blocks if any of the five validation stages fails. `GATE-BUILD-011` (signing) blocks if the signing service rejects the request or the signature does not verify. `GATE-BUILD-012` (runtime isolation) blocks if the CLI has any pipeline reference or runtime dependency. `GATE-BUILD-013` (reproducibility) blocks if a third-party reproducibility run does not reproduce the bundle. `GATE-BUILD-014` (audit completeness) blocks if the audit log entry for the release is missing any required field.

A release is published only when every gate has passed. The pipeline's release process records the gate results in the release metadata, so that a user who installs the bundle can see which gates passed and which evidence supported each.

## Open questions and unresolved decisions

Six open questions remain. `OPEN-BUILD-01` asks whether the pipeline will support incremental builds in which only the changed GVKs or rules are regenerated, or whether it will always perform a full build; the current design performs a full build for determinism, but incremental builds could reduce the build time for frequent releases. `OPEN-BUILD-02` asks whether the pipeline's signing stage should use a hardware security module (HSM) or the multi-party approval workflow described in `OFFLINE_UPDATE_AND_SIGNING.md`; the current design allows both, but the project must choose one as the default before the first production release. `OPEN-BUILD-03` asks whether the reproducibility test should be run on every release or only on major releases; the current design runs it on every release, but the cost is significant. `OPEN-BUILD-04` asks whether the source fetch should use the official Kubernetes GitHub repository or a mirror; the current design uses the official repository and verifies against the tag object, but a mirror with verified caching could reduce the build time. `OPEN-BUILD-05` asks whether the benchmark corpus should be part of the pipeline repository or a separate repository; the current design keeps it in the pipeline repository, but a separate repository would allow independent maintenance. `OPEN-BUILD-06` asks whether the pipeline should produce a machine-readable "attestation" document (in the SLSA or in-toto format) that a third party can verify; the current design records the same information in the release metadata, but a standard attestation format would improve interoperability.

## Definition of done

This document is complete when ten conditions hold. The governing principles (deterministic generation, pinned sources, provenance by construction, fail-closed, isolation between pipeline and runtime) are stated and derive every requirement. The pipeline overview defines the fourteen stages, the four phases, and the DAG. The acquisition phase specifies source pinning, source verification, provenance collection, and license collection. The generation phase specifies schema extraction, schema normalization, rule validation, lifecycle and feature-gate merging, and index building. The validation phase specifies static checks, unit tests, regression tests, fuzzing, compatibility tests, and benchmark gates. The publication phase specifies bundle assembly, verification, signing, artifact publishing, release metadata, and audit logging. Every stage has an input, an output, a set of validation rules, a set of failure conditions, and a gate. Every gate (`GATE-BUILD-001` through `GATE-BUILD-014`) is defined and blocks the release if it fails. The constraint that the connected pipeline never becomes a runtime dependency is stated as `BUILD-REQ-044` through `BUILD-REQ-048` and is enforced by `GATE-BUILD-012`. The reproducibility mechanism is specified with the two-run test and the third-party verification. The rollback, emergency fix, and source update workflows are specified. The dependency pinning and isolated build environments are specified. Every requirement has a stable ID (`BUILD-REQ-NNN`), every stage has a stable ID (`STAGE-<NAME>-NNN`), every gate has a stable ID (`GATE-BUILD-NNN`), and every test has a stable ID (`BUILD-TEST-NNN`). The document does not claim any implementation status, benchmark result, or verified detection rate, and it does not promise that any stage is currently implemented — it specifies the stages, the gates, and the evidence each requires, and it leaves the implementation to the pipeline's code, which the release process audits at every release.

The knowledge build pipeline is the mechanism by which KubeCheck's knowledge is produced, verified, and published. It is not a build system for the CLI; it is a build system for the bundle, and the bundle is the artifact the CLI consumes. The separation is architectural, not incidental, and it is the reason the offline CLI can trust the bundle it loads: every claim the bundle makes is a claim the pipeline verified against a pinned source, a reproducible generation, a comprehensive test suite, a benchmark gate, and a signed release. The pipeline's job is to make those claims true; the CLI's job is to verify them at load time; and the user's job is to decide which bundles to install. The pipeline is designed so that each of those jobs can be done without trusting the other two.
